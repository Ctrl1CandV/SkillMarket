# 实验计划：四个方法技能

图论课程设计那两次试用，没有真正用上 tdd、diagnose、codebase-design 和 code-reviewer。这里给每个技能各设计一个小任务，用 pi + deepseek-flash 各跑一次。

- 每次都加载 dev-kit 的全部 6 个技能，提示词里不点技能名，同时看描述能不能让技能被自动用上。
- 题目、夹具和评判标准都在开跑前写好、提交入库，跑完不改。
- 运行脚本：[run_exp.sh](run_exp.sh)。夹具：[fixtures/](fixtures/)。

每个实验的提示词末尾都加一句：“我不在，有需要我决定的地方按你的推荐决定，并写明你的决定。”

## E1 tdd：地铁票价模块

**任务**：空仓库，只有一份需求（[需求.md](fixtures/e1-tdd/需求.md)）。分段计价加月度累计折扣，规则里有几个边界值和四舍五入。
**提示词**：按 需求.md 实现地铁票价模块。核心计费逻辑要先写测试，再写实现。

**通过标准**：
1. 读了 tdd 技能。
2. 写测试之前，先写下要在哪些接口上测，每个接口说明能发现什么问题。
3. 按竖切片推进：每一轮先写一个测试，跑出失败，再写实现让它通过；不能先把全部测试一次写完。工具调用的顺序里，至少要能看到 3 轮“写测试 → 跑出失败 → 写实现 → 跑通过”。
4. 测试的预期值来自需求里手算的数字，不能用和实现一样的公式再算一遍（同义反复）。
5. **变异检验**（由优化者来做）：往实现里分别注入 3 个错误：6 公里的边界改成严格小于；12 到 32 公里不足 10 公里时不进位；折扣门槛 150 改成大于而不是大于等于。三个错误都要被测试抓到。

## E2 diagnose：AA 分账偶尔少一分钱

**任务**：小项目里有分账函数、命令行入口和测试，现有测试全部通过。

- 真正的原因：`int(total * 100)` 截断浮点数。比如 19.99 × 100 = 1998.999…，截断后变成 1998，于是少一分钱。
- 干扰项：最近一次提交改了命令行输出格式，反馈里也提到了这次改动。

**提示词**：看一下 反馈.md 里用户反馈的问题，查清原因并修好。

**通过标准**：
1. 读了 diagnose 技能。
2. 动手猜原因之前，先做出一条在这个 bug 上会变红的复现命令，跑过，并贴出输出。
3. 列出至少两个可证伪的猜想，并核对过输出格式那次改动不是原因。
4. 找到真正的原因，即浮点乘以 100 后被截断。
5. 修复前先写一个失败的回归测试，修复后通过；原有测试也全部通过。
6. 收尾时清掉临时日志和临时脚本，汇报里写明原因。

## E3 codebase-design：图书角借还书接口

**任务**：`library.py` 是一组很浅的函数，两个调用方各自按顺序调用五六个函数。其中自助借书机漏掉了“借满 5 本”和“查无此人”两项检查。
**提示词**：借书流程散在两个调用方里，经常漏步骤。帮我重新设计 library 的借还书接口，给几种方案比较，推荐一种。先别改代码。

**通过标准**：
1. 读了 codebase-design 技能，以及 DESIGN-IT-TWICE.md。
2. 给出至少两种形状真正不同的方案，而不只是改名字。每种都写出接口、调用示例、错误由谁处理，以及从现有调用方迁移的代价。
3. 用深度、局部性和接缝位置来比较，给出明确的推荐，并说明在什么情况下别的方案更好。
4. 推荐的方案能让两个调用方不再漏掉这两项检查。
5. 不改代码：工作区里除了新增的说明文档，没有别的改动。

## E4 code-reviewer：订单分页与导出

**任务**：main 分支上是订单查询，feature 分支在这之上加了按客户分页和导出 CSV。项目约定写在 CONTRIBUTING.md 里。

埋了 5 个问题：
1. 用 f-string 把客户名直接拼进 SQL，可以注入。
2. 用 `except Exception` 吞掉所有错误，然后返回空列表。
3. 分页切片少取一条：`start + size - 1`。
4. 导出时 `open` 不关闭，也没有用 `with`，违反项目约定。
5. 新加的行为没有测试。

另外放了一个不算问题的地方：`scripts/` 下用 `print`，项目约定明确允许。

**提示词**：帮我审查 feature 分支相对 main 的改动，只报告，不要改代码。

**通过标准**：
1. 读了 code-reviewer 技能。
2. 第 1 到第 4 个问题至少找出 3 个，每个都写清位置、触发条件、后果和改法。
3. 指出第 5 个问题（缺测试）。
4. 不报 `scripts/` 下的 `print`，也不把风格偏好当成缺陷。
5. 写明跑过哪些检查；用了三个脚本的话，记下脚本有没有提供人工审查之外的新发现。

**脚本去留**：优化者把三个脚本放在这份夹具上，也自己运行一次。只有在它们能指出至少一个真实问题、而且误报不多时，才保留。
