# skill-search 触发条件与范围审查

日期：2026-10-06。根据用户对初稿的反馈，将 `skill-search` 调整为 v0.2.0，保留“找到能改善当前任务的技能”这一目标。本文记录静态审查与修改，不包含新的联网生态核验或真实宿主试跑；初稿记录见 [design-review-2026-10-06.md](design-review-2026-10-06.md)。

## 审查结论

“读研需求优先检查本地 grad-companion”包含两个不同层次的判断：先检查已有能力，可以减少重复搜索；指定某个插件，却依赖个人环境，也容易截断用户要求的外部搜索。把通用原则写成“检查已有能力，只搜实际缺口”，从 description 与正文移除固定插件路由。前端、工作流与研究只保留为检索目标的例子，不限定可检索领域。

“不检索 GitHub 开源项目”原本用于区分技能发现与软件项目发现。检索对象需要写清，但 GitHub 也承载技能原始文件，强否定容易让来源核验被误读为越界。description 聚焦技能发现，正文区分目录发现、原始来源核验和混合请求中的软件项目检索，不增加通用项目检索流程。

用户补充的复杂项目场景暴露了初稿的另一个缺口：一次性不等于简单，复杂也不自动意味着值得搜。新版允许为复杂项目中可解释的能力缺口主动找技能；普通任务直接做，明确技能搜索则按要求完成。泛泛“搜索论文”或“搜索项目”不作为本技能触发依据。

## 修改范围

| 初稿行为 | v0.2.0 行为 | 预期改善 |
| --- | --- | --- |
| description 列举个人高频领域与指定插件 | 明确技能搜索，或复杂项目中可由专项方法改善的环节 | 触发依据来自任务需要，减少环境绑定 |
| 读研类固定路由到四个插件技能 | 所有领域先检查已有能力，按实际缺口确定目标 | 可独立安装；不冒充依赖已存在 |
| 本地缺失后须用户明确说找外部替代 | 已明确搜索或有合理主动检索依据时可继续外部检索 | 避免二次询问同一意图 |
| 已有技能可能提前结束发现 | 用户要求外部搜索或比较时，已有技能作比较基线 | 不让复用偏好覆盖明确请求 |
| 一次性任务作为刹车 | 普通任务直接做，复杂的一次性任务按增量判断 | 支持复杂实施场景 |
| “不检索 GitHub 项目”作为触发边界 | 正文明确技能是对象、GitHub 等可作原始来源 | 保留职责范围，允许候选核验 |
| 两轮后须用户要求扩大才继续 | 通常两轮，新线索或明确覆盖要求可追加 | 保留停止纪律，允许有依据的追查 |

保留命令自校验、官方来源优先、读正文与必要资源、指标口径检查、低安装量信号、飞书污染反例与授权范围。未添加 API 客户端、领域专用依赖或额外运行文件。

## 静态场景审查

以下为按规则逐项推演，不是独立代理执行结果。

| 请求或情形 | 应采取的行为 |
| --- | --- |
| “帮我改一次按钮间距” | 直接做，不搜索 |
| “这次要打通跨工具流程，并按领域规范完成多阶段核验” | 先指出薄弱环节及技能预期增量，再有针对性检索；不能仅凭提示词长就搜 |
| “找能写引言的 skill”，没有 grad-companion | 按写作目标检索，不要求先安装插件或补说“外部替代” |
| “我已有一个阅读 skill，帮我比较外部替代” | 把现有能力作基线，继续外部检索与比较 |
| “搜索这几篇论文” | 按论文检索需求处理，不自动变成找技能 |
| “这个 GitHub 仓库里有适合我的技能吗” | 读取真实技能文件核验；不因 GitHub 来源而拒绝，也不将普通软件仓库当技能 |
| “找工作流 skill，再找可配套的开源软件” | 技能检索按本方法，软件发现由宿主相应能力处理 |
| 论文查询返回高热度飞书文档与邮件技能 | 按正文排除，必要时改词；不强推、不套固定插件 |
| 连续两轮词面检索无合适结果 | 如实说明；仅有具体新线索或覆盖要求时追加，否则回到已授权任务 |
