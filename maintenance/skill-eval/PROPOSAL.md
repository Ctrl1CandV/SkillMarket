# skill-eval 立案

日期：2026-10-24。状态：**仅立案，暂不实施**。依据用户本轮明确要求，仅在 dev 的 maintenance 保留计划，不创建运行 Skill、命令、执行脚本或评测服务。

## 要回答的问题

一轮 Skill 修改，在用户真实任务上改善了什么、退化了什么，需要多少生成和返工成本？先服务本仓库，不先建通用评测平台。受欢迎的上游只能提供方法候选，不能充当本地有效性的证据。

## 启动前需要满足的条件

- 真实且有代表性的任务和原始输入已经确定，允许保存用于比较的最小材料；开发样例、回归案例与未用于调规则的留出任务分开。
- 基线版本可冻结并追溯；比较组拥有明确的内容、功能、工具、模型与预算口径。无 Skill 基线仅在它能回答实际问题时加入。
- 先定义质量维度和不可接受的退化：任务完成、事实准确、信息可找、视觉/表达符合目标、可访问性等按任务选择，不用一个总分掩盖失败。
- 明确重复次数的理由、可接受总成本、停止条件和评审者；不把此前建议的 18 次生成当统一配额。
- 区分原始模型产物、人工/模型返工、静态检查和实际运行；可追溯到任务、提示、模型设置、Skill 版本、产物、评价与成本记录。

## 可复用的最小形态（待设计）

优先整理现有维护资料中的任务记录和评审方法，确定人工能跑通的流程后，再决定是否需要轻量 Plugin 或脚本。候选产物是任务清单、运行记录、匿名配对评审、结果与成本汇总；此处只是范围，不是已定接口。

审美主观评价优先匹配用户自己的日用场景。匿名比较可减轻版本预期影响，但评审应同时看到真实功能、内容与必要状态；需要说明谁评了什么。使用 LLM 评审需校准与记录分歧，不能代替用户审美。受个别任务启发改过规则后，该任务只能作为开发/回归案例，不能继续称独立留出。

为判断 Skill 的日常总收益，应允许它作出合理的信息架构选择并记录差异；若单独研究视觉样式，则需控制内容与功能等价。两种问题分开设计，避免把新增功能直接算成纯审美优势。

## 首个候选对象与边界

frontend-craft 可作为首个候选：现有报告与产物仅是方法资产，先核对版本、人工干预、已参与调参的任务和成本口径。本轮 frontend-craft 的实际检查属于其自身验证，不等于 skill-eval 已实现，也不预先证明跨模型收益。

未来实施前再调研活跃的 Skill 评测方案和一手评估方法，记录适配理由；此阶段不引入运行依赖、不建立排名榜、不自动运行付费调用，也不将私有任务上传第三方。
