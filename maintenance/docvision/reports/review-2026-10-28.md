# docvision 0.1.0-rc.1 审查：论文阅读、准确率与速度

- 日期：2026-10-28（Asia/Shanghai）。
- 审查基线：dev，`4e4cf77`。只审查与试跑，没有修改技能实现、安装依赖、上传文档或提交 Git。
- 目标：8 GB / 16 GB 消费级显卡，日常 PDF/PNG，尤其论文公式、表格与架构图。
- 结论：**选型合理，已有可用的本地论文解析基础；当前仍应作为候选版，不能认定已达到稳定、优秀的端到端阅读效果。先修工作流与环境问题，再做真实样本比较，优先级高于增加 provider。**

## 1. 与当前开源方案的关系

docvision 是引擎适配、输出整理与阅读流程，不是一个新 OCR 模型。实际效果由模型、推理运行时、参数、文档类型、输出保真度和上层视觉模型共同决定。

2026-10-28 核查的 [OmniDocBench 官方 v1.6_full 表](https://github.com/opendatalab/OmniDocBench#end-to-end-evaluation)中：PaddleOCR-VL-1.6 为 96.34，MinerU2.5-Pro 为 95.75，GLM-OCR 为 95.22，DeepSeek-OCR 2 为 90.25。榜上另有更高条目，因此可以说当前两个主引擎属于优秀开源候选，不能宣称最强。

该表 Overall 平均正文编辑距离、公式 CDM、表格 TEDS，**不评估架构图箭头、模块关系与数据流的解释**，也不是关键公式完全正确的概率。MinerU 4.x 是工具版本，MinerU2.5-Pro 是模型系列；本机标准档有 GGUF 模型，不能直接继承榜单所用配置的分数。

[MinerU 官方硬件说明](https://github.com/opendatalab/MinerU/blob/master/docs/en/usage/tiers.md)明确，8 GB 显存只是部署规划起点，不能保证所有负载；性能取决于 VLM 运行时、输入和并发。16 GB 本机能运行标准档，但本轮没有验证 8 GB、长论文与峰值显存。现阶段两台机器都先用单并发，测量后再决定是否开两个进程。

## 2. 新增真实论文试跑

来源：[Attention Is All You Need，arXiv v7](https://arxiv.org/abs/1706.03762)。下载公开 PDF，取原第 3、4、8 页组成三页 PDF，分别覆盖 Transformer 架构图、attention 公式与合并单元格表格。转换过程中只用本地引擎。

- 原 PDF：15 页；SHA256 `bdfaa68d8984f0dc02beaca527b76f207d99b666d31d1da728ee0728182df697`。
- 三页样本 SHA256：`ccdd3a6432da6571715a6e1c1444f75c1669cb52788273574586b00e8d121a27`。
- 机器：Windows 10，RTX 4070 Ti SUPER 16 GB，31.8 GB RAM，Python 3.12.9。
- 引擎：MinerU 4.0.12；PaddleOCR 3.7.0 / PaddlePaddle GPU 3.2.1，发现的 PaddleX 3.7.2。
- 时间是 CLI 报告的单文件 elapsed，包含引擎发现与进程/模型启动。每种模式仅一次，模型已在本机缓存；没有做冷热启动控制或统计显著性比较。

| 路线 | 结果 | 耗时 | 人工核对 |
|---|---|---:|---|
| MinerU standard / auto | 成功，3 页，qa pass | 19.47 秒 | 架构图资源和核心 attention 公式保留；表格末两行跨列单元格被拆开；脚注求和公式顺序损坏 |
| MinerU standard / ocr | 成功，3 页，qa pass | 15.92 秒 | 同一脚注恢复 `q·k = sum(q_i k_i)` 的 LaTeX 结构，表格训练成本恢复 colspan=2；核心 attention 公式保留 |
| PaddleOCR local | 失败，没有页面 JSON | 8.76 秒 | PaddleX 提示 OCR extra 依赖缺失，不能据此比较速度或准确率 |

强制 OCR 改善了这份样本的两处错误，说明路由/模式选择会实质影响质量；不能由三页推断所有论文准确率，也不能由第二次更快推断 OCR 比 auto 更快。没有在本轮跑 quality 档。

补充：最初终端显示的乘号异常经 UTF-8 文件核对是控制台显示问题；原文件为 U+00B7，两个输出均没有 U+FFFD。实际错误是脚注公式结构与表格跨列关系，不能把控制台显示当成 OCR 错字。

架构图在结果中主要表现为图片资源和图注；这证明图被保留，不证明系统已正确理解图中的模块连接。需要让使用技能的视觉模型实际打开图块，并结合图注和正文验证关系。

复现实测的基本命令（输入为上述三页样本）：

```text
python docvision/scripts/docvision.py convert attention-selected.pdf --provider mineru-local --tier standard --mode auto --keep-raw --output <auto-output> --json
python docvision/scripts/docvision.py convert attention-selected.pdf --provider mineru-local --tier standard --mode ocr --keep-raw --output <ocr-output> --json
python docvision/scripts/docvision.py convert attention-selected.pdf --provider paddleocr-local --output <paddle-output> --json
```

原样本和完整原始结果留在系统临时目录，未收入仓库。精简核查记录见 [review-summary-2026-10-28.json](../evals/review-summary-2026-10-28.json)。

## 3. 确认的实现问题

### P1：缺页与选错页可以通过 QA

`docvision/scripts/dv/verify.py:54-59` 从实际返回页号的最大值推断应有页号，未对照 `meta.source.pages`；存在 `options.pages` 时直接跳过缺页检查。

无网络临时 fixture 已复现：源元信息为 12 页、结果只有第 1 页，返回 pass；要求第 3–5 页、结果只有第 1 页，同样 pass。长论文缺尾页和错误引用可能漏检。应比较预期页集合与实际页集合；无法知道完整页数时明确标为未验证。

### P1：resume 会跳过改善质量所需的重跑

`docvision/scripts/dv/cli.py:50-58,84-89` 仅按源 SHA256 查已有结果，忽略页范围、provider、模型、mode、tier 和已有 QA 状态。

真实复现：先生成上述 auto 结果，再对同一输出根目录执行 `--mode ocr --resume`，返回 skipped，仍指向有脚注/表格错误的 auto 输出。换模型、提高质量或改选页也可能复用旧结果。应把影响输出的参数与版本纳入缓存匹配，至少明确提示配置不匹配。

### P1：Paddle 主 Markdown 与按页读取中的图片链接可能失效

`docvision/scripts/dv/providers/paddle_local.py:53-68,143-146` 保留上游页面 Markdown，后续 `_crop_image_blocks` 生成另一组图片文件；代码没有复制上游 `imgs/` 或把页面正文链接映射到新裁图。

离线 fixture 复现：正文仍引用 `imgs/img_in_image_box_0_0_1_1.jpg`，实际仅有 `assets/page-0001-image-1.png`；块级 asset 可用，正文/按页 read 仍坏链，QA 仅 warn。应统一正文与块资源，避免读取论文图形时丢图。本轮真实 Paddle 受依赖问题阻塞，未把该 fixture 冒充真实推理结果。

### P1：core 环境没有连接到 CLI 的渲染、拆页、裁剪执行路径

`docvision/scripts/dv/setup_cmd.py:181` 安装独立 `docvision-core`，但 `util.py:396,448` 等在启动 CLI 的当前解释器直接导入 pypdf、pypdfium2、Pillow，没有切换/调用 core 环境。

因此干净机器按 SKILL 的系统 `python docvision.py` 命令运行，即使安装 core，仍会报依赖缺失并再次建议安装 core。本机全局包遮掩了该问题；禁用外部 site packages 的最小实验确认当前解释器的导入路径不会因 core 配置而改变。应提供统一入口、明确在 core 中启动，或将相关操作发给 core 的 Python。

### P2：页面缓存忽略 DPI，妨碍小字图与公式复核

`docvision/scripts/dv/read.py:123-125` 仅以页码缓存渲染结果。先按默认 150 DPI 查看，再要求 400 DPI 裁剪，会直接复用 150 DPI 页面。stub 复现真正渲染调用只有 `[150]`。缓存应包含 DPI，或在更高分辨率请求时重渲染。

### P2：空正文没有按技能约定判 fail

`output.py:73,96` 给空结果补一页和固定头；`verify.py:42` 检查整个 Markdown 文件是否非空，固定头使 empty_markdown 检查失效。零正文、零资源的临时结果仅为 warn/blank_pages。应检查正文及块内容，而非含元信息头的文件。

### P2：小图和多文件使用有可避免的固定启动损耗

`detect.py:66` 自动路线先检查全部引擎，`config.py:191` 包括 Paddle 导入，然后 `mineru_local.py:35` 再次发现 MinerU。此次独立只读计时：MinerU 发现约 1.313 秒，Paddle 发现约 5.984 秒，尚未开始 OCR。

每文件又启动独立引擎进程，重复初始化。应先短路查找默认引擎，批次内缓存发现结果；日用高频小图再考虑常驻服务。现有文档的本地 2–4 并发建议没有显存与吞吐实测，不能当成通用提速方法。

## 4. 当前 Paddle 环境问题

doctor 显示 Paddle available，整体 healthy=true；实际转换却在管线构建时失败。只读核对发现当前 PaddleX 的 OCR extra 缺 beautifulsoup4，触发 require_extra 错误。

不能指控 setup 忘记安装 extra：PaddleOCR 3.7.0 元信息确实声明 doc-parser → paddlex[genai-client,ocr]。但当前 conda 环境会优先读取用户全局 Python312/site-packages；禁用 user site 后，环境本体还缺若干依赖，名义隔离没有达到独立可复现的效果。

应修正安装/运行的用户包隔离方式，并增加真正构建管线或最小单页推理的就绪校验。整体 healthy=true 只表示有可用路线，当前 MinerU 正常不能代替 Paddle 验证。此次未安装或修复该环境。

## 5. 值得保留的设计

- 本地失败不会静默上传；远程授权有显式开关。
- 页、块、bbox、公式、HTML 表格和原图资源，为引用和回看提供了基础。
- 按页阅读、关键公式回看页面、把 OCR 文本当数据，均适合 AI 读论文。
- 维护报告明确承认合成样本、远程 mock、8 GB 未测的边界。
- 当前 MinerU CLI 的 image_analysis 默认开启；不能把适配器未传 chart 开关解释成 MinerU 默认禁用图形分析。

## 6. 下一版验收顺序

1. 修复完整页集合校验、resume 参数匹配、Paddle 图片保留和 core 执行环境；修好当前 Paddle 依赖并真实试跑。
2. 把公式/表格难页的 auto 与强制 OCR/quality 做同页对照，加入本文脚注和跨列表格作为回归案例。
3. 选约 20–30 页公开真实材料，覆盖英文双栏论文、中文扫描、密集公式、跨列表格、折线图与架构图；记录各自错误，保留同页原图供核对。
4. 在 8 GB 和 16 GB 各测端到端冷启动、连续批处理、峰值显存、长文档失败率。先单并发，确认余量后再测双并发。
5. 对架构图明确检验模块名、箭头方向、跨模块连接和图文对应；OCR 输出后让视觉模型打开原图，不能只评估图注转写。

这五项完成后，再讨论默认引擎是否切换。继续接入更多云服务目前不是最关键的工作。
