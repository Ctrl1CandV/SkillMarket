# git-governance 1.0.1 简要审查

## 结论与修复

原 1.0.0 可作为通用工作流指导，能够区分 Git 机制、分支用途、发布包与本地文件，但对 Agent 的两类实际失误仍有执行缺口：分类没有落实为精确提交清单，消息质量没有明确验收条件。已将修复后的版本标为 1.0.1。

- 入口要求形成当前任务与目标分支的路径清单，逐项对账 staged 的新增、修改、删除和改名，提交后再次检查真实快照。
- 文件参考补齐 `testt/`、正式测试、`private/`、Agent 临时资料和项目文档的默认处理与例外；保留未知文件的本地副本，先阻止其进入提交。
- 明确运行必需的 references/scripts/templates 需要随 skill 交付；维护评测不能混入运行目录，不能一律忽略正式测试或文档。
- 提交参考增加对象/变化、快照一致性、逻辑拆分和真实验证的验收，以及本仓库描述式消息与 Conventional Commits 的自拟例子。
- 规范模板增加每个分支的必须保留/允许维护/排除内容，并要求说明 staged 清单的对账方式。

## 参考核对

按用户建议采用 skill-search 的方法，先查看已有技能；已读取本地 ECC `git-workflow` 的正文作为比较基线。它覆盖工作流与消息格式，但没有解决本仓库的运行/维护资料分支隔离；其中固定人数/频率与批量清理示例不适合直接继承。GitHub 搜索未返回相应正文，文件接口也未取得可读内容，因此没有声称核验其上游当前版本，没有安装新技能。机制依据仍使用 skill 中已列出的官方来源。

GitHub 插件成功读取本仓库远端 main/dev 的当前引用；与后续 Git fetch 的结果一致。其 GitHub workflow 查询接口不可用，`.github` 目录不存在，未声称验证了平台所有部署或保护配置。

## 项目分支与本次范围

仓库 README 和 maintenance README 明确：main 收录运行资源与索引，dev 另保留 maintenance。根目录 README 补充了这项规则及私人资料/一次性草稿的排除要求。

| 分支 | 本次文件范围 | 提交组织 |
|---|---|---|
| main | README + git-governance 入口、4 份参考、项目规范模板 | 一笔运行资源提交，不合并整棵 dev |
| dev | 同样的运行资源；maintenance 索引、操作语义检查与两份验证/审查报告 | 运行资源和维护记录分成两笔提交 |

两个分支各有一笔此前已提交但未推送的 presentation-craft 更改。用户明确选择本次一并推送，以保持本地与远端同步；main 的那笔只含运行资源，dev 的那笔另含其维护评测。工作区其他 grad-radar 修改不在本次提交范围。

## 验证与限制

修复后结构验证通过，运行文档的 9 个本地相对引用全部可解析；原 9 项隔离 Git 仓库操作语义用例再次通过。人工复核：临时 testt/private 不暂存、正式回归测试依项目规则保留、必要参考文档随运行 skill 发布、维护记录仅入 dev、含无关 staged 内容时不直接 commit、最终标题必须对应快照。

这些是语义测试和人工决策路径复核，不能证明所有模型永远不会误提交。skill 能提供可执行的规则与阻止点；实际 Agent 仍需遵循清单并核查结果。平台强制检查或自动扫描尚未配置。
