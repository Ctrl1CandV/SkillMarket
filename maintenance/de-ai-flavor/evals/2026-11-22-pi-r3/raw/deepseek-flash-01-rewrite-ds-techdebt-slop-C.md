**为什么很多团队的技术债清理专项最后都不了了之**

每年年初，总有团队要立一个技术债清理专项。启动会上领导拍板，从各组建个虚拟小组，双周同步一次。头两次会人还挺齐，第三次开始有人请假，后面基本就是主持人在群里发个进度。再过一阵，群里最后一条消息是“最近业务紧，先缓一缓”。

这个专项从头到尾没人反对过。它没被谁否决，只是在一次次排期里被慢慢稀释掉了。这才最值得琢磨。

**一、它被当成项目立项，本质却是一笔利息**

项目有三个特征：边界清楚、有交付物、有结束时间。技术债清理一条都不占。你说不清哪个模块算“重构完了”，因为下个月需求一压上来，它又开始变脏。

技术债这个叫法，重点从来不在本金，在利息。改一个字段要动好多个地方，发版前得手工核对几张表，半夜被同一条早就麻木的告警叫起来。这些都是利息，是每天都要往外付的钱。

而“专项”这个词默认了一次性还本、之后不再借。可业务压力摆在那儿，你早晚还得借。所以这类专项注定收不了尾：它想解决的是存量清零，真正没人管的却是利率。

**二、清单是工程师的语言，决策者看的是风险**

那份清单打开来，`order_service` 拆分、补齐核心链路单测、MQ 消费幂等改造。每一条都正确，但没有一条能答上决策者要问的那句话：不做会怎样，什么时候出事，出事要赔多少钱、拉多少人进去。

排期表上通常只放两类东西：能挣钱的，和能少赔钱的。技术债清理不翻译成后者，就上不了表。它很少在评审会上被砍掉，因为它根本走不到评审会。

**三、收益看不见，成本当场兑现**

重构支付链路做三个月，成了没人知道，因为没上新功能；中途出一次资损，全公司都知道是你干的。理性的人不会主动推这种事。

业务需求反过来，上线当天就有数据，做好了算功劳，做砸了还能说是在快速试错。人跟着激励走，跟责任心关系不大。

**四、抽人封闭，死得最快**

抽几个人封闭两周，这个姿态最像下决心，其实最不经折腾。人被抽走就成了稀缺资源，业务一告急，第一个被抽回去的就是他们，而且抽人的时候也没人觉得自己在干坏事。

它还顺手给全公司种下一个错误印象：技术债是额外的事，得等额外的时间。额外的时间永远等不来。

**五、真要推，就别管本金，去管利率**

先把利息变成看得见的数。变更失败率、发布前置时间、构建时长、oncall 被打扰的次数、告警里真正需要处理的比例、新人第一个 PR 合进去要多久。这些让流水线每周自动产出，不用谁去写 PPT，指标一恶化自己就进管理层视野了。这里有个坑得提前防：指标一旦挂上考核，一定有人把它做漂亮，比如把告警批量静音、把大构建拆成几个小的。所以只看趋势，别拿去给个人排名。

第二件事是往需求里夹带，不单独立项。任何一次改动，都允许带上一部分成本，顺手把它碰到的脏东西清掉。boy scout rule 说顺手清理自己碰过的代码，听着像道德倡议，其实是排期策略，因为它不需要预算审批。不过夹带在评审时会被砍价，“你这 PR 为什么多改这么多”一句话就能把人噎回去，所以最好在 PR 描述里提前写清楚顺手清了哪些。另外也别指望夹带能解决结构性的问题，动骨架的事还是得单独要窗口。

第三，只清正在流血的。别做全量重构，盯住那些改得最频繁、也最容易出问题的模块，拿 git 修改频次乘上故障数排个序，排在前面的才是真债，剩下的多半只是不好看。顺带把手工步骤写进 runbook 并标上耗时，让“每次发版多花四十分钟”这种话有据可依，比讲十遍架构原则管用得多。

回过头看，技术债清理专项失败，很少是因为团队不专业或者不努力。多数时候是时间尺度用错了：拿季度项目去解决一个按天计息的问题。

还不清。只能把利率压到一个不疼的水平，然后接受它一直存在。
