## 二、需要测试机完成的任务

总原则沿用 0.2.0：不升级原 ComfyUI/Python/PyTorch/节点，不改原启动器；权重固定 revision 与 SHA-256；GPU 空闲才跑；云端每张单独提交、不自动重抽；图片与回执留仓库外，仓库只放脱敏记录。

### 任务 1：补测 Z-Image Turbo，决定本机默认模型（最重要）

**为什么**：0.2.0 的本机对照测了 FLUX.2 klein、Mage-Flow Turbo、Ovis-Image、LongCat-Image，漏了目前公认文字能力最好、又能在 16 GB 上跑的 Apache-2.0 模型 Z-Image Turbo。"本机写字接近 100% 失败"的结论因此只对这四款成立。它的加装成本很低：Comfy-Org 包里的 `qwen_3_4b.safetensors` 与 imagecraft 已固定的文本编码器**哈希完全相同**，只需新增扩散模型和 VAE。

官方工作流：`Comfy-Org/workflow_templates` @ `c067929d7e9cc0f3fd15be348fa1a1d85da15946` 的 `templates/image_z_image_turbo.json` 与 `image_z_image_turbo_int8.json`。审查方读到的参数：`UNETLoader` → `CLIPLoader(qwen_3_4b, type=lumina2)` → `CLIPTextEncode`，负向为 `ConditioningZeroOut`；`EmptySD3LatentImage`；`ModelSamplingAuraFlow(shift=3)`；`KSampler(steps=8, cfg=1, res_multistep, simple, denoise=1)`；`VAELoader(ae.safetensors)`。以测试机 `/object_info` 为准。

步骤：

1. 先用 `/object_info` 确认现有 ComfyUI 0.31.0 原生支持上述节点和 `lumina2` 类型；int8_convrot 能在不升级的前提下加载就优先 int8（6.2 GB），否则用 bf16。任何一项需要升级时停下来报告，不改原环境。
2. 同 seed、同尺寸，klein 与 Z-Image Turbo 各跑以下三组，每题 2 个 seed：
   - 冻结的 v2 真实用途题（论文图、中文方法图、产品页），直接复用 0.2.0 的题目和计分口径，便于和四款旧结果并表。
   - **新增低密度文字题**（本机最可能用到、0.2.0 没测的一档），建议 5 题：中文海报主标题 4–8 字；英文幻灯片封面（标题＋副标题）；店招一行英文；3 个标签的简单流程图；书封（中文书名＋作者名）。逐字计分。
   - 视觉题：`suites/focused-v1.json` 的 13、16、18（写实人物）、19、20（动漫）各一项，加一张无字 Hero 底图。由人看图评"可用/不可用"并写理由。
3. 记录单张服务端耗时、整卡显存与系统内存峰值、冷启动耗时。
4. 写入 `eval-z-image-turbo-2026-11-xx.md`，并把结果并入 `references/routing.md` 的实测表。

决策规则（审查方建议，测试机可附理由调整）：

- Z-Image Turbo 在低密度文字题上明显好于 klein，且视觉题不差 → 改为本机默认文生图模型；klein 保留作参考图编辑（Z-Image Turbo 只有文生图）。
- 两者各有胜负 → 两个都保留，按用途分档：文字/写实走 Z-Image，编辑/极速探索走 klein。
- Z-Image 没有明显优势 → 维持 klein，路由表注明已测并给出数据。

若改默认或双模型：需要把 `models/` 清单、`workflows/`、`download_models.py` 的仓库白名单、`ic/workflow.py`（`build` 按模型选图结构，`CORE_NODES` 增 `EmptySD3LatentImage`、`ModelSamplingAuraFlow`、`KSampler`；`CORE_MODULES` 增对应模块）、`jobs.prepare_request` 的清单哈希、`--model` 参数和单元测试一起改。共享文本编码器只下一次，`models plan` 要能看出复用。

**Qwen-Image 2.1（可选，先问用户）**：7B，文字与多图编辑很强，但许可是 Qwen Research License（非商用），文本编码器 int8 9.35 GB＋模型 int8 7.26 GB，官方模板需要较新的 ComfyUI 节点（`TextEncodeQwenImage21`、`QwenImage21Cache`），现有 0.31.0 大概率不支持。只有用户接受非商用许可、并同意另建隔离的 ComfyUI 时才测；否则在 routing.md 里写明"未采用：许可与版本要求"。Qwen-Image-2512（20B，Apache-2.0）在 16 GB 上过重，不测。

### 任务 2：用显存预留模拟 12 GB / 8 GB

**为什么**：硬件闸目前只有 16 GB 一个数据点。新增的 `serve --reserve-vram` 可在同一张卡上近似小卡。

步骤：分别以 `--reserve-vram 6.5`（约 9.5 GB 可用，近似 12 GB 卡扣掉桌面占用）与 `--reserve-vram 10.5`（约 5.5 GB 可用，近似 8 GB 卡）启动；对当前默认模型各跑 1024×1024 与 1536×1024 两张，记录成功与否、耗时、系统内存峰值。8 GB 档再试一次 `qwen_3_4b_fp8_mixed` 文本编码器。

验收：把结果写进 routing.md 的硬件闸表，"12 GB 可以试"改为有数据的结论；若 8 GB 档能稳定出图，把它从"直接走 GPT"改成"可试，较慢"，并写清条件。注明这是模拟，不等于真实小卡。

### 任务 3：GPT 订阅出图做成可执行脚本

**为什么**：技能的核心定位之一是给"只会写字"的宿主补上出图能力，可云端这一路在技能里没有可运行的入口，新机器上的宿主只能照着文字临场拼 app-server 协议。测试机已有外部探针和 Plus 登录，适合在这里落地。

要求：

1. 先实测 cloud-fallback.md 里写的 `codex exec --skip-git-repo-check -C <dir> '$imagegen <prompt>'` 在当前 Codex CLI 版本上能否出图、文件落在哪里。能用就以它为基础；不能用就以已验证的 app-server 流程为基础，并改正文档里的命令。
2. 新增 `scripts/cloud_codex.py`（或 `imagecraft.py cloud ...` 子命令），只用标准库。功能：
   - 预检：`codex` 在 PATH 上；`codex login status` 为 ChatGPT 模式，API key 模式直接退出；`modelProvider/capabilities/read` 报告 `imageGeneration`。
   - 读提交前额度（`account/rateLimits/read` 的 `usedPercent`、`windowDurationMins`、`resetsAt`，按池识别，不假定 `primary` 就是 5 小时窗口）。
   - 只提交一个回合；取图优先 `item/completed` 的 `savedPath`，其次内联结果解码，最后 `$CODEX_HOME/generated_images/<thread>/`；复制到 `--output` 指定的新目录（建议 `<project>/.imagecraft/jobs/<slug>/image.png`），解码、记录尺寸与 SHA-256。
   - 读提交后额度。
   - `job.json` 分开记录提交、生成、取回、额度观测四个状态；额度读失败不影响"生成成功"的判定。回执不明时只允许 `status/resume` 查原线程，不提供自动重交。
   - 不读 `auth.json`，不设置或读取 API key，不购买 credits；只把 `--prompt-file` 与显式 `--reference` 发出去。
3. 单元测试：用假 app-server（stdio JSON-RPC）覆盖 API key 模式拒绝、无 imageGeneration 能力、只有预览无文件、额度读取失败但图片成功、回执不明不重交、输出目录已存在拒绝覆盖。
4. 真实验收（经用户同意，最多 2 张）：一张无字素材、一张中文高密度界面视觉稿，记录耗时与额度差。
5. 更新 cloud-fallback.md 的"每张图怎么做"，改为调用脚本；SKILL.md 的三路径表与首用说明同步。

### 任务 4：验证本机提示词写法

**为什么**：审查方新增的两条本机写法（正面描述替代否定词、宿主扩写为 120–300 词英文段落）有通用依据，但没在 klein 上实测。

步骤：选 3 个 brief（产品素材、页面方向稿、人物），每个做 2×2：短提示 vs 扩写段落 × 含否定词 vs 正面描述，各 2 个 seed，共 24 张，约 2 分钟 GPU。人看图评：是否出现了被否定的元素、构图是否更贴 brief。另测一次色值（如 `#C8643B`）是否比"暖色"更稳。结论写进 eval 记录；若不成立，改回或修正 task-briefs.md 的对应条目。

### 任务 1：完成，保留分用途双模型，不切默认

原生节点和 INT8 convrot 实际加载通过，BF16 文本编码器复用 FLUX 同哈希文件，Z 的 VAE 单独核验。14 题 × 两 seed × 两模型的 56 张全部完成、逐图看过并回查哈希/尺寸/请求。低密度逐字得分 Z **14/18**、FLUX **6/18**，完整低密度文字/版面契约为 **5/10 对 2/10**；指定视觉用途为 **8/12 对 10/12**，Z 四张全身图均裁头。复杂图示均未满足完整节点/有向边契约。

因此 FLUX 仍是极速素材/编辑默认，短中文标题等显式选 Z，不把 Z 自动推广为写实默认。已同步三份固定清单、两种原生图结构、下载器白名单与共享说明、请求清单/模板哈希、`--model`、相关测试、SKILL 和路由。Z BF16 文本方案后续服务端中位数 24.035 秒，FLUX 为 3.914 秒；首次 Z 加载与 FLUX 切模分别记录，不把后者称全冷进程。详见 [评测](eval-z-image-turbo-2026-11-02.md) 与 [逐图结果](results/z-image-comparison-v1.json)。Qwen-Image 2.1 未下载或测试，未获非商用许可及另建核心授权。

### 任务 2：完成预留模拟，真小卡仍未验证

`reserve-vram 6.5/10.5` 下，默认 FLUX 的 1024² 与 1536×1024 各成功一次，服务端分别为 5.292/3.664 秒和 4.572/5.616 秒；均已看图、核对并写入人工 review。10.5 档另显式测 Z 的 FP8 mixed 文本编码器一次，23.192 秒、整卡最大 **8863 MiB**，不称“Z 8GB 已验证”，也没有把它说成默认 FLUX 的自动降精度或质量等价方案。
