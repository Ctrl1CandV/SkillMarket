内部小工具、10 人团队，**先用 SQLite**，除非你有下面这些明确需求。

## SQLite 更合适的情况

- 内部工具、读多写少、并发用户 <20
- 部署简单优先：一个文件就是数据库，不用运维、不用备份脚本（复制文件即可）
- 单机部署、或数据量在几 GB 以内
- 原型/MVP 阶段，不想先花时间搞基础设施

注意 SQLite 的并发模型：写操作是库级串行加锁（WAL 模式下读写可并行，但同一时刻只有一个写者）。10 人级别的内部工具完全够用，但如果"高频写入"是你的核心特征，要提前想清楚。

## 选 PostgreSQL 的情况

- 数据以后要长成正式业务系统，不想迁移
- 需要多实例/多服务共享同一份数据（SQLite 是文件，网络共享文件做数据库非常危险）
- 并发写入频繁，或需要行级锁、复杂事务
- 需要 JSONB、全文检索、窗口函数、物化视图、PG 扩展等
- 团队本来就有 PG 运维经验，或已有托管实例（云上 RDS 成本很低）

## 我的建议

**MVP 阶段 SQLite → 真长起来了再迁 PG**，因为从 SQLite 迁 PG 的成本主要在 SQL 方言和并发语义上，如果一开始就用 ORM 和标准 SQL，迁移不难。

但如果这个工具预期生命周期长、会持续加功能、有多个服务要接，**直接上 PG 更省事**——省的是未来的迁移和重构，不是现在。

## 快速判断

| 情况 | 选 |
|---|---|
| 单机、少量用户、快速上线 | SQLite |
| 会做成长期业务系统 / 多服务共享 | PostgreSQL |
| 已有 PG 实例可用 | PostgreSQL |
| 团队没人想运维数据库 | SQLite |

如果告诉我这个工具大概做什么、部署在哪（单机/容器/云）、是否会有多个服务访问，我可以给更确定的答案。
