# SQLite vs PostgreSQL：10 人内部小工具

先说结论：**绝大多数情况下选 SQLite**，除非命中下面几个"红线"。

## 关键判断：这是一个"工具"还是"服务"？

选型的核心不是用户数（10 人），而是**并发写入模式和部署形态**。

---

## 选 SQLite 的情况（推荐）

- **单机部署、数据量不大**（< 几十 GB）、写入不频繁
- 10 人同时**读**完全没问题，SQLite 支持并发读
- 写入是"偶尔点一下保存"，不是高频批量写入
- 团队不想运维数据库（无 DBA、无额外服务器）
- 希望**零依赖**：一个文件就是整个数据库，备份=复制文件

> SQLite 的并发限制是"同一时刻只能有一个写者"，但写是毫秒级的，10 人的内部工具几乎不可能撞上写锁竞争。真正的瓶颈是**大量并发写**，不是用户数。

## 选 PostgreSQL 的情况

- **多台服务器/多实例**需要共享同一份数据（SQLite 不行，文件不能跨机共享）
- **高频并发写入**（比如后台大量任务同时写库）
- 需要**强类型的复杂查询**、窗口函数、CTE、JSONB、全文检索、PostGIS 等
- 需要**细粒度权限控制**、行级安全
- 数据很重要，需要成熟的 PITR 备份、流复制、高可用
- 团队已经有 PG 运维经验 / 已有 PG 实例

---

## 快速决策表

| 关注点 | SQLite | PostgreSQL |
|---|---|---|
| 运维成本 | 几乎为零 | 需装、配、备份、升级 |
| 部署 | 单文件，跟着程序走 | 独立服务 |
| 并发读 | 好 | 好 |
| 并发写 | 有限（单写者） | 好 |
| 多机共享 | ❌ | ✅ |
| 复杂查询/数据类型 | 够用但弱 | 强 |
| 扩展规模 | 单机为主 | 可水平/垂直扩展 |
| 备份 | 复制文件 | pg_dump / PITR |

---

## 我的建议

**先上 SQLite，并预留迁移路径：**

1. 用 ORM（如 Prisma / SQLAlchemy / GORM）或统一的数据访问层，避免写死 SQLite 特有语法
2. 数据量、并发写入一旦触到瓶颈，再切 PostgreSQL（表结构基本可平移）
3. 提前想好：**如果未来要多人跨机访问或加后台批处理**，那就直接上 PostgreSQL，省一次迁移
