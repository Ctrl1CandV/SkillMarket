## 3. 复杂技术回复：解释连贯，操作可执行

方法：编辑者模型在同一会话读取并应用仓库修订稿，生成以下回复，再做自查。测试任务是现实排障场景的构造输入，不声称实际连接了数据库。这是模型试跑，非独立评审、自动触发验证或跨 Harness 验证；没有隔离上下文、无技能对照或重复采样。

输入：

> 我们有两个应用实例，PostgreSQL 里 jobs.status 默认是 queued。每个实例先用 SELECT id FROM jobs WHERE status = 'queued' LIMIT 1 找任务，再 UPDATE jobs SET status = 'running' WHERE id = $1，两条语句各自自动提交。偶尔同一个任务执行两次。请解释为什么，给一个可以改的 SQL 方案和验证步骤，别把长解释切成一句一段，也别为了紧凑把 SQL 和步骤塞进大段话。任务是在数据库事务之外执行的；失败后还需要重试。不要承诺 exactly-once。

模型输出：

````markdown
两个实例可能在任何一个 UPDATE 提交前查到同一个 queued 任务。SELECT 没有锁住这条任务，而后面的 UPDATE 只按 id 更新，没有检查它是否仍是 queued；即使更新时行锁让两个 UPDATE 先后执行，两边仍可能认为自己领取成功。问题在于“找到任务”和“认领任务”没有组成一个受并发控制的原子操作。

可以在一个短事务内锁定并更新待领取的行，只有拿到 RETURNING 结果的实例才执行任务。下面假设 id 唯一，按 id 选择任务；SKIP LOCKED 让另一个实例跳过正在被领取的行，而不是等待同一条记录。

```sql
BEGIN;
WITH candidate AS (
    SELECT id
    FROM jobs
    WHERE status = 'queued'
    ORDER BY id
    LIMIT 1
    FOR UPDATE SKIP LOCKED
)
UPDATE jobs AS j
SET status = 'running'
FROM candidate AS c
WHERE j.id = c.id
RETURNING j.id;
COMMIT;
```

应用必须确认事务成功提交，并且确实返回了任务 id，才在事务外执行任务；没有返回行就表示这次没领到任务。不要把外部任务执行放在领取事务内长期持锁。这个方案解决的是并发领取冲突，不保证任务的外部效果只发生一次。

重试需要单独设计：进程可能在认领后崩溃，也可能已经完成外部操作，却还没来得及标记任务完成。仅凭 running 状态无法判断是哪一种；通常需要增加租约到期时间、重试次数和每次领取的令牌，并让续租和完成更新核对令牌，避免旧执行者覆盖新执行者的状态。租约过期也不代表旧执行者已停止，因此外部效果还需要幂等键或接收端去重；现有表结构和外部接口能力未给出，不能据此承诺 exactly-once。

验证时建议在测试库按下面顺序做：

1. 放入一条 queued 任务，连接 A 执行 BEGIN 和认领语句但暂不 COMMIT。连接 B 执行同样的认领事务，应不返回这条被锁定的任务；随后分别提交，并检查任务状态。
2. 放入多条 queued 任务，用两个实例并发领取，记录各次 RETURNING 的 id。没有重新入队的前提下，每条任务只应被成功领取一次；再让 A 在提交前回滚，确认该任务仍可被其他连接领取。
3. 在测试环境模拟“提交领取后崩溃”和“外部操作成功后、写完成状态前崩溃”。先观察当前方案的恢复缺口，再在实现租约及幂等后复测，确认任务能恢复且重复尝试不会重复产生外部效果。
````
