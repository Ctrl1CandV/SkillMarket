上学期你们用红黑树手写过 map，这学期翻开 MySQL 手册，InnoDB 的聚簇索引是 B+ 树。每次讲到这儿总有人抬头问：哈希表查一次就命中，红黑树也是 O(log n)，凭什么是 B+ 树当默认答案。

这个疑问卡在一个地方：你们把 O(1) 里的那个 1 当成了一次真实的操作。在内存里它确实是一次。可索引不在内存里，它躺在磁盘上，那里一次“操作”的单位不是一条指令，是一整次页读取。

一次内存随机访问大概 100 纳秒。一次 SSD 随机读一页 100 微秒上下，机械盘要 10 毫秒。磁盘上的“一次”比内存的“一次”贵三到五个数量级。到了这个量级，O(1) 和 O(log n) 前面的常数不再是次要项，它变成了唯一重要的项。剩下的问题只有一个：谁的层数更少。

一百万条记录，红黑树高度是 log₂(10⁶)，约 20 层，因为二叉树每个节点最多两个叉，一次比较只能排除一半。B+ 树把一个节点做成一整页。索引项是 8 字节主键加 6 字节页号，14 字节，16KB 一页除下来装得下一千一百多个，扇出就是一千一百。log₁₁₀₀(10⁶) 不到 2。三层 B+ 树能覆盖十亿条记录，而三层里根节点基本常驻 buffer pool，真正的物理 I/O 只有两次。二十次对两次，还没算红黑树那二十次里有一半是随机寻道。

红黑树还有一笔更隐蔽的账。它是一个节点一个 key，可磁盘读写的最小单位是一页。你为了拿一个 key 把整页搬进内存，那一页里剩下的空间付了钱却没用上。B+ 树把一页塞满，每次 I/O 都把带宽榨干。这算不上算法上的花招，它只是把“读一页”这个不可再分的成本摊到最薄。

哈希呢？等值查询上哈希是真赢，一次 I/O 定位到桶，O(1) 就是 O(1)。但它只回答“key 等于 42 的那一行”。你写 where id > 100 order by id limit 20，哈希索引帮不上任何忙——哈希函数把相邻的 key 打散进不同的桶，顺序关系被彻底毁掉了。范围扫描、排序、前缀匹配、联合索引的最左前缀，这些在真实业务里占了一多半，哈希结构在这里的问题在于它没法把顺序表达出来，谈不上快慢。InnoDB 里确实有自适应哈希索引，但那只是给热点页加的一层内存缓存，骨架仍然是 B+ 树；真正把哈希当主结构的，只有 MEMORY 这类全内存的表。

再说为什么是 B+ 树而不是 B 树。B 树的非叶节点也存行数据，挤掉了本该放页号的空间，扇出变小，树就长高了；更要命的是范围扫描得在层与层之间来回回溯。B+ 树的非叶节点只放 key 和页号，叶子节点用双向链表串起来。拿到一个范围，它只做两件事：找到起点，顺着链表走。

回到开头那个问题。数据结构的选择不是复杂度排行榜上谁的名次高，而是被两件事夹出来的：数据放在哪里，用户怎么问它。你们的内存是纳秒级的，数据库的磁盘是微秒到毫秒级的。红黑树在内存里是极好的东西，原样搬到盘上，就成了拿二十次寻道换一次顺序读。以后你们真去写存储引擎，第一个要问自己的问题应该是：我这里的“一次操作”，到底有多贵。
