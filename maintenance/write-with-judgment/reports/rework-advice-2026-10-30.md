# write-with-judgment 改造建议

日期：2026-10-30。性质：静态审阅后的实施指导，本轮没有改运行文件，也没有跑模型试验。依据是 0.2.1 运行包四个文件、[0.2.1 修订记录](revision-0.2.1.md)、0.1.0 存档，以及用户反馈：多轮实测中，这个 Skill 的表达均不如不加 Skill。原始实测记录不在本仓库。

## 结论

0.1.0 到 0.2.1 的主干几乎没变，变的只是补充的边界条件。问题出在 Skill 的写法和形态，不在缺哪条规则，所以继续加规则不会变好。建议先做路线 A：退役本 Skill，把少数有用的内容并入重做后的 de-ai-flavor（见 [de-ai-flavor 改造建议](../../de-ai-flavor/reports/rework-advice-2026-10-30.md)）。如果实测记录显示某类文体确实需要单独处理，再按路线 B 为它写一个短 Skill。

## 问题、原因与策略

### 1. Skill 本身就是 AI 腔，模型会照着学

**现象。** 主文件开头是“让文字呈现值得接触的内容，并使这些内容在阅读中成立：一个区别被看清，一项判断获得依据，一种处境或感受有了具体形状。”全篇大量使用“成立、展开、承接、分量、依据、判断”等抽象名词，句子四平八稳。

**原因。** 模型会模仿提示词的语体。七千多字这种文字读进去，输出就被拉向更抽象、更审慎、更像评论的方向。在“不如不加”的差距里，这一条大概占比最大。

**策略。** 运行文字本身就用希望输出具有的语体写：短句、具体动词、明确态度。验收时把 Skill 的每一句拿它自己的标准检查一遍；抽象名词能换成可观察的动作就换，比如“让内容在阅读中成立”改成“先写读者最想知道的那件事”。

### 2. 每条指令都同时肯定正反两面，净方向接近零

**现象。** “解释可以减少推断困难，也可能遮住重心；重复可以提醒、积累或凝聚，也可能使阅读停滞。”“删除后某种效果仍在，不证明原表达毫无作用。”平均 88 字出现一处否定或对冲。

**原因。** 一个做法和它的反面同时被认可，模型就推不出该往哪边走，只能回到“看情境”，而这本来就是它的默认状态。剩下的作用只有谨慎：少补细节、少下判断、能保留就保留，输出也跟着对冲。

**策略。**
- 每条写作指导只给一个方向，最多附一个最常见的例外。
- 少数硬约束集中写一次：不改事实和证据强弱，不冒充亲历，不编数据。
- 边界情况放进例子里展示，不要在每句话后面追加。
- 把否定、对冲词的平均间隔作为静态检查项，目标不低于 200 字一处（readable-reply 的水平）。

### 3. 把评价者的认识论当成写作程序

**现象。** “有据、值得、及时”三问，以及“不能把整体收益全部归因于某个词句或顺序变化”“模型的阅读判断不代替独立读者反馈”“不将本 Skill 的条目数变成分数”。

**原因。** 这些是比较版本、做实验时的方法论，从研究过程漏进了运行时指令。写作时一边生成一边对照三维评价框架，产出往往正确但拘谨，还多耗一份注意力和 token。修订记录也能说明这一点：0.2.1 的取舍几乎都在讲“怎样判断才不武断”。

**策略。** 评价方法放进维护目录的评测协议。运行文件只写写作动作，比如找出读者的问题、找到最具体的那件事并先写它、删掉换个主题也成立的句子。“只作诊断”模式确实是在做评价，可以保留一份五六行的检查单。

### 4. 没有一段好文字当靶子

**现象。** 三份参考里没有一段可以模仿的好中文。choices.md 的例子大多在讲“什么时候不要改”，比如周报两版、手链那段。

**原因。** 用户在 frontend-craft 上的经验是正面范例远胜规则。这个 Skill 既没有范例，也没有可操作的清单，只剩抽象权衡，模型找不到具体的目标形态。

**策略。** 每种目标文体放两三段真正好的现代中文，每段附一两行说明它做对了什么具体动作。优先用同一内容的“AI 初稿 → 好版本”对照，读者能直接看到改动。来源可以是用户自己认可的文字、获准使用的课程材料，或注明出处的短摘录。范例不能取自评测输入。

### 5. 触发范围太宽，而无 Skill 基线本来就不低

**现象。** description 覆盖文章、说明、讲稿、沟通文案、评论与叙事，几乎等于“所有写作”。

**原因。** 强模型在熟悉文体上的默认输出已经接近上限。对这些任务，一份通用指令能带来的主要是干扰和额外成本，很难有净收益。

**策略。** 只针对实测中无 Skill 输出明显偏弱的文体，例如长篇论证、情感叙事或讲稿（需要用实测记录确认）。在证明有效之前，可以设成只能手动调用（`disable-model-invocation: true`，Claude Code 字段），避免自动触发拖累日常写作。

### 6. 迭代由审阅意见驱动，而不是由读者偏好驱动

**现象。** 0.1.0 由一个模型编写，0.2.0 由另一个模型送审修订，0.2.1 再整合；整个过程只做了静态审阅，没有效果试验。

**原因。** 每条审阅意见都会变成一句防御条款。按“挑不出毛病”优化出来的文字，天然面面俱到、处处平衡，而这正是 AI 味的核心特征。

**策略。** 规则只因输出中观察到的失败而加入，每条都能对应一个具体的坏输出。关于认识论的审阅意见写进维护报告，不进运行包。版本是否更好，只看冻结输入上的盲评结果。

### 7. 情感与叙事被过度约束

**现象。** emotion-and-voice.md 用大段篇幅讲“不替作者补原因”“新增内容要核对依据或授权”“动作、感受词与直抒胸臆都不是天然优选”。

**原因。** 非虚构的事实边界有必要，但写成全篇主调以后，在允许虚构的任务里也会压掉读者最喜欢的东西：具体的细节、果断的意象、有力的结尾。

**策略。** 非虚构只保留一条硬约束：不冒充作者的经历和原因。虚构与创意任务正面鼓励具体的虚构细节、明确的意象和结尾，并配一两段好例子。

## 两条路线

**路线 A：退役并入（推荐）。** 删除本 Skill，以下内容并入重做后的 de-ai-flavor：
- choices.md 里“平均数 180、中位数 100”的例子：不加外部事实，只展开已有材料之间的关系，就能让文字更有内容。
- “先备份再切换”的例子：操作前提要放在读者需要的位置。
- 改稿时保留事实、立场和证据强弱。

两套通用写作 Skill 并存会分散触发，而且两者有同类问题，合并后只需维护一套。

**路线 B：重写为短 Skill。** 仅当实测记录表明某类文体需要专门方法时采用：
- 主文件约 1500 字以内，只写这类文体的三到五个关键写作动作。
- `references/exemplars.md` 放范例和前后对照。
- 硬约束一段，不展开认识论。

## 实施与验收步骤

1. **整理旧实测。** 把用户已有的实测记录（输入、各版本输出、判断）整理进本目录，找出无 Skill 胜出最明显的文体和句型，作为新版要越过的基线。
2. **冻结输入。** 准备开发集和留出集，覆盖目标文体；改规则时参考过的任务只能算开发集。
3. **写新版。** 按上面的策略写，交付前跑两项静态检查：否定和对冲词的平均间隔，以及主文件长度。
4. **盲评。** 同一模型下，比较无 Skill、新版，以及可选的旧版，输出顺序随机、版本匿名。评审除用户外，尽量加入一两位其他读者，例如之前合作研究中的文学专业学生，并记录 token 成本。
5. **判定。** 新版在留出集上多数不差于无 Skill、且没有任何文体明显落后，才算可用；否则执行路线 A 或直接退役。

## 不建议继续做的事

- 继续追加“保留的情况”和边界说明。
- 再做一轮只有静态审阅的交叉修订。
- 用 AI 检测分数、禁词命中数或规则条目数衡量效果。
