# 练习日记：带着 modern-web-guidance 做三页（2026-11-18）

目的：改 frontend-craft 之前，先亲手做几页交互多的页面，弄清楚 Google 的指南在真实页面里哪些规则真正起作用，哪些问题它管不到。三页都是先查指南、读完再动手。核对脚本放在 [checks/](checks/)，截图放在本地临时目录，没有入库。

| 页 | 场景 | 主要用到的指南 | 核对结果 |
|---|---|---|---|
| [p1](p1-repair-desk/index.html) | 物业报修派单台：撤销确认、行内菜单、提示条 | dialog、viewport-aware-dropdowns、persistent-toast-notifications | 交互核对 16/17，剩下 1 条是脚本误报；pagecheck 修改后没有问题 |
| [p2](p2-swim-signup/index.html) | 游泳班报名表单（家长在手机上填） | forms、validate-input-after-interaction、accessible-error-announcement | 表单核对 20/20 |
| [p3](p3-power-bill/index.html) | 家庭电费月账单：深浅色、往月表格 | dark-mode、dark-mode-toggle、color、responsive-table | 主题核对 16/16（含修改后补的一项） |

核对用的是 Chrome 157。锚点定位、命令按钮（invoker commands）、`closedby`、`light-dark()` 都已原生支持，所以这三页都没有加 polyfill。

## 指南真正改变了做法的地方

1. **原生对话框省掉了一大块代码。** 用 `<dialog>` 加 `showModal()`，不写焦点陷阱，也不写 Esc 处理。默认焦点放在“保留工单”这个安全按钮上。关闭后，浏览器自己把焦点还给了触发按钮；即使触发按钮在一个已经关上的菜单里，焦点也回到了打开那个菜单的“⋯”按钮。我原来的习惯是自己写焦点管理，容易漏掉一半。
2. **行内菜单不用 JS 定位。** 用 `popover` 加按钮的隐式锚点，再写 `position-area` 和 `position-try-fallbacks`，菜单就贴着按钮，碰到边缘会自己翻转。指南还专门提醒：这是“装在浮层里的一组按钮”，不是 ARIA 菜单，所以不要加 `role="menu"`，也不要加 `aria-haspopup`。Firefox 还不支持锚点定位，在那里菜单会出现在屏幕正中，要按目标浏览器决定加不加 polyfill。
3. **提示条的规则改变了设计。**
   - 对话框打开时不弹提示，等关闭后再出；
   - 提示里的信息在页面别处也必须找得到，所以我把每次操作都写进了工单的“记录”；
   - 用 `popover="manual"` 放在一个固定的通知区里，配一个关闭按钮；
   - 用 `ariaNotify` 播报，不支持时退回到 live region。
4. **表单把提示放到了输入框上方。** 理由是手机键盘和自动填充的弹窗会盖住输入框下方的内容。这是指南改变版式的一处，frontend-craft 以前没有这一条。
5. **表单的触控尺寸不小于 48px。** pagecheck 现在的门槛是 40px，表单里应该按 48px 要求。
6. **错误出现的时机。**
   - 用 `:user-invalid`：只经过、没输入不报错；写错离开才报；改对以后立刻消失。
   - `aria-invalid` 和 `aria-describedby` 要跟着它同步。
   - 提交失败时把焦点移到错误汇总，汇总里的链接直接跳到对应字段。
   - 提交成功后立刻停用按钮，防止重复提交。
7. **深色模式的落地方式。**
   - 用 `<meta name="color-scheme" content="light dark">`，再在 `:root` 里用 `:has()` 把 meta 的值映射成 `color-scheme`。
   - 颜色用 `light-dark()`。
   - 做成三态切换（跟随系统、浅色、深色），默认跟随系统，选择存在 localStorage 里，在 head 里用一小段内联脚本先读取，防止闪一下错误的主题。
   - 根元素上不要写死 `color-scheme: light`。这一条和 frontend-craft 起步样例的做法相反。
8. **字号用 rem，带文字的元素不写死高度。** 画面上看不出差别，但把文字间距放大到 WCAG 1.4.12 的值以后没有任何裁切。这类规则能用脚本检查，适合放进 pagecheck。

## 指南没有、要由我们补上的

1. **深色模式下的淡底要和卡片底色混。** 指南的配色篇说：生成浅一点、深一点的颜色时，和白色或黑色混。在深色模式里，选中行和选中按钮的淡底如果和黑色混，会比卡片还暗，看起来像个洞。正确做法是和卡片底色混。
2. **一个颜色变量不要身兼几个角色。** 高对比度偏好下我把边框色调深了，进度条的轨道也用着同一个变量，结果进度条对轨道的对比度掉到 1.4。拆成单独的 `--track` 后，对比度恢复到 5.5。
3. **`:user-invalid` 的出错样式只给文本类输入框。** 指南的示例写的是 `input:user-invalid`，单选和勾选框也会被画上红色的半圆。
4. **版式问题仍然要靠 frontend-craft 和看图。** 这些问题 Google 的规则一条都没指出：
   - 320px 宽度下横向溢出；
   - 房号按钮只有 26px 高；
   - `all: unset` 把房号的大字号清掉了，房号不再是最显眼的；
   - “800 元”在“元”前面断行；
   - 手机上的底部汇总栏占了 150px；
   - 手机上表格卡片在固定高度里形成了套叠滚动。

## pagecheck 的问题

- **颜色解析有缺陷。** 它直接从颜色字符串里抽数字。`color-mix` 算出的颜色是 `oklab(0.935 -0.005 -0.012)`，被当成接近黑色，于是报出对比度只有 1.27 的误报。改法：在页面里用 canvas 把颜色转成 sRGB 再算，我在 theme-check 里就是这么做的。改技能时必须先修好这一处，否则我们一边推荐 `color-mix`，检查脚本一边误报。
- **默认宽度要加 320。** 320 是 WCAG 1.4.10 规定的重排宽度，p1 的横向溢出只在 320 下出现。
- **可以从三个核对脚本里提炼进 pagecheck 或新脚本的检查：**
  - 字号是不是 px；
  - 带文字的元素有没有写死高度；
  - 放大文字间距后有没有裁切；
  - 根元素有没有声明 `color-scheme`；
  - 强制颜色模式下截一张图。

  对话框的 Esc 和焦点归还、表单出错的时机，和页面结构绑得太紧，更适合写成 review.md 里“手动或用流程脚本核对”的条目。

## 对改 frontend-craft 的含义

1. **SKILL.md 加一步。** 遇到浮层、表单、深色模式、动效、无障碍、性能时，先用 modern-web-guidance 查，交付时写明用了哪几篇。
2. **visual-style.md 改三处：**
   - OKLCH 调明度改成 `color-mix`；
   - 深色模式的淡底和卡片底色混；
   - 每个角色一个颜色变量。
3. **cjk-typography.md 的起点改用 rem 写法**，每行 30–40 个汉字不变。
4. **local-interfaces.md 或 review.md 补上：**
   - 表单提示放在输入框上方，触控 48px；
   - 浮层用原生元素。
5. **起步样例：**
   - 字号改 rem；
   - 带文字的控件改成 `min-block-size`；
   - 加 `color-scheme`；
   - 强制颜色模式下给选中态加轮廓。
6. **pagecheck：**
   - 修好颜色解析；
   - 默认宽度加 320；
   - 新增字号单位、固定高度、文字间距、`color-scheme` 四项检查。
