# 多信息、多功能局部界面设计：优化策略与实施摘要

编写日期：2026-10-28；范围修订：2026-10-29。

范围：frontend-craft 0.5.0-rc.1 与 product-design 0.2.0-rc.1 的下一轮定向优化。

状态：2026-10-29 已按本计划完成运行技能、参考与样张补强，并完成三题六个独立原型的新旧对比；保留本文件作为计划依据。实际结果、差异与局限见[实施与对比报告](local-interface-implementation-2026-10-29.md)。未修改已安装副本、提交或发布。

## 1. 本轮问题与目标

用户明确指出：PaperDesk 的三个局部界面用于说明技能在小界面、小窗口设计上的不足，不是本轮需要修复的对象，也不是必须逐一制作的样张或验收题。此前计划把问题来源当成实施与验收范围，现予以纠正。

本轮优化目标是：在有限且合理的空间内，把多种信息、多种功能及其状态组织成清楚、完整、协调的界面。适用对象包括信息卡、侧栏、抽屉、弹窗，以及完整页面内承担一个相对独立任务的区域；不以固定像素宽度定义“小界面”。

| 问题来源，仅用于诊断 | 用户指出的问题 | 应提炼的通用能力 |
| --- | --- | --- |
| API 配置 | 十多个展示项分布散乱，按钮、下划线小字、下拉框、选择框混杂 | 异质信息的归属与分组、功能依赖、操作层级、成组控件的视觉秩序 |
| AI 对话框 | 同一窗口两处下拉／查询区域效果重叠，妨碍阅读 | 多个功能区域的职责区分、重复入口处理、空间竞争与上下文连续 |
| 导读信息卡 | 多个折叠框意义不明、视觉不佳，内容提取仍不充分 | 内容提炼、解释与扫描的分工、可见性判断、整体阅读顺序 |

这些问题说明，单个控件成立和整体页面成立，并不保证中间尺度的功能区域也设计得好。技能需要在“整页构图”和“单控件样式”之间，提供局部信息与功能组织的具体判断方法。

当前规则已有分组、连续阅读和组合状态原则，本轮补足的是它们在复杂局部界面中共同作用的决策过程、参考和示例。改动应帮助执行者作出更好的设计，不能只归结为执行不足，也不能把 PaperDesk 的具体修改意见变成通用模板。

局部重设计可以改变分组、顺序、显隐和操作组织，保留当前有效的产品事实与外层关系。外层布局被认可不自动把局部任务限制为 CSS 微调；功能多也不自动要求拆页、加 Tab 或套若干卡片。

## 2. 设计策略

### 2.1 先整理局部任务和内容，再选控件

对本次涉及的内容说明它支持哪个判断或动作、依附哪个对象、何时需要，以及更新后影响什么。复杂案例可用短工作表整理，但不要求日常任务提交固定表格。

| 内容性质 | 组织方式 |
| --- | --- |
| 当前判断或操作的必要依据 | 直接可得，邻近所支持的决定 |
| 同一对象的状态、字段与恢复动作 | 放回同一语义分组，避免状态与操作散落在不同角落 |
| 条件成立才需要的参数 | 随真实依赖出现，入口和作用范围清楚 |
| 可复用但低频的设置或资料 | 保留明确路径，不持续占据主体阅读空间 |
| 重复解释或实现机制 | 合并、移出使用者界面或不显示；保留必要能力与事实 |

筛选首先改变归属、顺序、分量和出现时机，不通过删除必要字段、限制条件或既有能力制造整洁。分组依据用户正在处理的对象和决定，不按“所有按钮一组、所有说明一组”排列。

### 2.2 让控件类型服从行为，让同类控件形成秩序

输入、选择、开关、执行动作和导航允许使用不同控件。应检查同一类动作是否有一致表达，标签和值是否可对齐，同层级按钮的高度、留白、基线和视觉重量是否相称。

“按钮饱满、对齐”转化为：有足够的可识别面积和内边距，与相应字段组及容器建立清楚的对齐关系，主次动作组成稳定区域。不能机械规定所有按钮相同颜色、固定宽度或都变成主按钮，也不能让主要动作退化为难发现的下划线小字。

即时切换、修改草稿、提交保存、导航和破坏性操作按实际后果区分。操作的范围与影响应从附近内容和反馈中理解，不能仅靠颜色区分；组合动作只有在产品确实执行组合行为时才能这样命名。

### 2.3 根据内容关系选择窗口容量与阅读方式

先消除重复和无效分区，再判断局部界面的可用空间。必要时调整窗口尺寸、分组布局或支持内容的呈现方式，不一开始就把每组内容折叠，也不为了少滚动持续缩字。

同一局部区域可能同时承载说明、属性、列表、预览、输入、状态和动作。按当前判断分配空间与视觉分量：需要比较的保持关联，需要解释的保留连贯，需要操作的保持可达。多个入口或内容区先判断职责是否重复，再决定合并、并置、切换或按需查看。

滚动区域由任务和容器决定；查看详情、返回、切换对象和结果更新时保留必要输入、选择及位置。空间调整同时保护内容可读性、操作可达与外层已成立关系，不建立“一律全展开”“一律折叠”或“只能一个滚动条”的禁令。

### 2.4 同时检验内容、功能与视觉完成度

信息完整但排列散乱、功能可用但控件轻重失衡，仍不算完成。把整个局部界面作为一个画面，检查主次、对齐、分组间距、文字角色、表面层级和动作区是否共同成立。

审视展开后、错误出现后、内容变长后和多选后的组合结果。示例不能只有短标题、少量字段和理想成功态，也不能以缩字、删信息或隐藏主要功能获得“更简洁”的截图。

## 3. 用跨业务复杂任务验收可迁移能力

### 3.1 按关系复杂度选题

验收题需要同时包含多类信息、多项功能和相关状态，不能只是一个十几项输入框的表单，也不能把原 API、聊天或导读页面换名称后重测。题目给出真实任务、数据和功能边界，不预先指定分组、布局或控件答案。

可从以下方向选择少量、关系不同的任务；这是覆盖方向，不是已经冻结的题目或必须制作的三个产品：

| 关系类型 | 示例方向 | 要暴露的复杂度 |
| --- | --- | --- |
| 多项配置与条件依赖 | 批量图片导出窗口 | 预览、格式与尺寸依赖、命名冲突、输出位置、预设及执行状态共同出现 |
| 对象详情与多种操作 | 设备借用申请详情区域 | 人员、设备、时段、可用数量、交接与冲突信息，以及不同后果的处理操作 |
| 查询、比较与结果处理 | 素材检索与批量处理页 | 筛选、结果、预览、版本差异、多选及处理反馈之间的关系 |

任务覆盖页面中的局部区域和窗口，不只验证弹窗。用合理且统一的宿主空间约束，保留内容长度差异、必要解释、状态和动作。复杂度来自真实关系，而非为了达标凑字段数量。

### 3.2 指导示例与验收任务分开

运行技能中的示例用于解释方法，可以逐步修改；开发样例用于发现规则是否可执行。最终验收任务在候选规则与示例定稿后，由独立评估者补全具体材料，避免针对已知页面直接写答案。

验收题不能复制技能样张的文案、数据、布局或完整操作结构。不得把题目专属限制、预设答案或评分提示补进候选技能。若根据某一验收题的结果反复改规则，该题应视为开发用例，再补一个未用于调优的任务检查迁移；不无限扩展测试矩阵。

### 3.3 在相同条件下比较旧版与新版

- 保存当前技能包作为基线，固定任务、内容、功能、初始工程、素材、宿主空间及视口。
- 使用相同模型和执行条件，在隔离上下文中分别使用旧版与候选技能包；新增指导和参考属于候选包的一部分，不能把效果单独归因于某一句规则。
- 保留首轮输出，给予双方相同的必要复查机会。不能只手工精修新版再与旧版首稿比较，也不挑选最好的一次隐去其他结果。
- 将信息与功能逐项对照原任务，确认都准确保留或有合理可达路径；这是完整性检查，不是预设界面分组。
- 隐去版本名称，查看完整局部画面、实际字号及关键状态，并实际完成代表操作。记录具体优缺点和判断分歧。

### 3.4 评价维度与成功条件

| 维度 | 重点判断 |
| --- | --- |
| 信息组织 | 能否认清对象、理解内容、找到当前判断依据；说明与扫描是否各得其所 |
| 功能组织 | 功能归属、操作范围、依赖和结果是否清楚；常用动作与恢复路径是否可达 |
| 视觉完成度 | 控件体量、对齐、疏密、主次、文字和表面是否形成协调画面；不能只统计容器或按钮数量 |
| 空间与状态 | 长内容、窄窗口、展开、错误及选择变化后，内容和功能是否仍可理解、可用 |
| 保真与迁移 | 必要信息和功能有无丢失，不同任务是否能产生合适的不同解法，而不是套同一种结构 |

候选应在不同关系的未知任务中呈现可说明的改善，同时保留必要信息和功能，避免明显的视觉或操作退步。如果只在一种题型有效，应报告适用范围并继续定位；如果整体相当或有得有失，如实记录，不宣布普遍提升。

操作测试不能代替审美判断。实际画面需要人工比较，用户可直接查看匿名结果；没有用户偏好反馈时，不把代理的评审写成用户认可。

## 4. 技能分工与文件级实施摘要

frontend-craft 承担本轮主要改动：局部内容编排、空间分工、控件组合、视觉与操作验证。product-design 补充任务、状态、反馈范围及内容职责；不要求每次小窗口改版都重新调用产品设计流程。

建议新增一份按需加载的 `frontend-craft/references/local-interfaces.md`，集中承载多信息、多功能局部界面的组织方法与跨业务推演。示例覆盖不同关系，不围绕 PaperDesk 的三个组件编写修复指南。原参考保留通用职责及必要链接，不新建独立 skill。

| 拟改位置 | 实施内容 |
| --- | --- |
| frontend-craft/SKILL.md | 在内容关系和范围入口增加局部重排的触发条件，路由至局部界面参考；读取当前有效及已否定的局部约束 |
| frontend-craft/references/local-interfaces.md（新增） | 内容提炼、信息与功能分组、依赖与顺序、控件组合、动作范围、显隐与滚动；跨业务正例及适用条件 |
| frontend-craft/references/content.md、scenarios.md | 保留通用内容原则；在相应场景指向专门案例，避免重复整套方法 |
| frontend-craft/references/layout.md、visual-style.md、review.md | 必要时补方向与幅度、成组控件及局部诊断；已有滚动、可访问性、看图要求不重复加长 |
| frontend-craft/assets/style-lab/ 与 style-samples.md | 按方法示范需要补少量复杂局部样张，沿用现有主题；与最终验收任务分开，不强制对应原三个场景 |
| frontend-craft/references/exemplars.md、exemplar-index.json | 按内容形态、功能关系、交互复杂度与容器条件索引跨业务案例，保留证据状态含义 |
| product-design/references/examples.md | 必要时补充对象、任务、动作后果和状态关系的推演；不复制前端控件及排版规格 |
| product-design/references/product-context.md | 保存反馈对象、状态、认可范围、已否定方案及原因；新事实或用户要求变化时更新 |

这是拟改清单，不要求每个现有文件都追加段落。实施时如新参考已清楚承载内容，其他文件只加相关路由；未发现新缺口的文件保持原状。

## 5. 案例收集与使用

首批候选见 [局部界面参考清单](local-interface-reference-candidates-2026-10-28.md)。已有资料偏向 API 与学术阅读，应作为一部分方法来源保留，不能代表本轮能力覆盖。后续补充不同业务中的复杂编辑、导出、对象详情、查询比较、批量操作等画面，组件规范辅助理解组合关系。

每个被采用的案例至少回答：对应什么任务与状态；包含哪些信息形态和功能关系；哪些内容与动作被组织在一起；怎样处理依赖、密度及状态；哪些条件不同不能照搬。收集完整功能区域及关键变化，不用孤立按钮、空表单或营销裁图代表复杂界面。

先广泛收集，再按待解决关系精读少量案例；选择具有不同组织方式的来源，保留各自使用条件。中文、长标签、较多内容与组合状态用本地任务验证。案例用于学习方法，验收材料避免直接复用案例布局；不靠收集数量宣称覆盖充分。

外部来源、查看日期、页面状态、可借鉴关系和限制随条目保存。现有 candidate / documented / verified_visual 状态继续使用；只读文档不升级成 verified_visual。实际看图也不代表完成产品操作测试。许可未确认的图先保留链接，不作为可分发技能资产；原创组合样张与外部范例分开标识。

## 6. 实施顺序与完成条件

1. 提炼通用能力及适用条件，保存当前技能包作为基线；按关系复杂度补充跨业务案例。
2. 编写局部界面参考，用少量开发样例检验方法是否足够具体；更新必要入口与衔接，避免业务专用修复规则。
3. 整理可复用示例与参考索引，定稿候选技能；示例不兼作最终验收题。
4. 独立编写跨业务的复杂界面任务，按相同条件运行旧版和候选，检查完整性并匿名比较画面与操作。
5. 根据具体得失决定保留、修订或撤回改动；修订后的迁移判断保留未用于调优的任务。
6. 整理运行文件、参考资源、对比产物、实际证据及局限。版本更新、安装、提交或发布依后续实施范围处理。

完成条件是新版技能在多信息、多功能的跨业务任务中表现出更好的组织与呈现能力，而不只是能重做已知的三个组件。检查项数量和文案增长不代表成功；采用定向评估，不重开上一轮整站升级矩阵。

本文件的计划阶段没有运行界面回归或声称实际设计已改善；后续实施与验证已另行记录，结论以实施报告为准。两份 10 月 26 日反馈及本轮用户补充是问题依据；本次未独立走查 PaperDesk 工程或登录真实服务。
