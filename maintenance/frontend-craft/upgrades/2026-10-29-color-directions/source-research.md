# 配色与样式方向：一手来源核查

核查日期：2026-10-29。范围仅为新一轮配色、表面和状态搭配；上一轮局部界面组织已由 `2e691eb` 独立保存。本记录供模板设计参考，不改写上一轮验收结论。

## 证据范围

以下 6 组一手资料均已读取官方页面正文，状态为 **documented**。未在浏览器查看这些外部页面的实际像素，未操作其产品，未下载或复制外部图片。网页中的图片标题只能帮助定位资源，不能算已看图。方法可用于原创样张；原创样张的审美、可读性及交互仍须另行验证。

现有 `visual-style.md` 已涵盖整体明暗、面积、配对、语义色和对比底线。本轮的主要增量应是能查看、能选择、能复用的完整搭配及使用说明，而不是把以下知识再抄成长规则。

## 1. Radix Colors：将色阶分配给用途

来源：[色阶用途](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale)、[组合色板](https://www.radix-ui.com/colors/docs/palette-composition/composing-a-palette)。页面未标明发布日期；以上为核查日。

官方方法把背景、控件及其交互状态、边界、实底和文字分到不同色阶用途。实底的前景并非统一白色：浅亮的黄、薄荷等配色使用深字。中性色既可不带色，也可与强调色呼应；带色背景遇到大量彩色标签时可能冲突。

**转化为样张：** 每套方向包括内容面、文字、按钮填充与前景、选择面和焦点，不只提供主色；增加“亮底深字”的操作样例。把多色状态放回实际表面检查。

**边界：** Radix 的已设计色阶与特定配对保证不自动覆盖自定义色值；本文不会把 APCA 说明替代为 WCAG 通过结论。色调相近是一种选择，不是所有灰色必须染色。

## 2. Material：明确背景与其内容色的配对

来源：[Material Web Color](https://material-web.dev/theming/color/)、[Material 3 Color roles](https://m3.material.io/m3/pages/color-roles?s=m3)。前者正文成功读取；后者通过搜索索引读取正文，常规入口需要 JavaScript，未据此声称已渲染查看。页面未提供可靠的发布日期。

Material 的角色把填充色与其上文字/图标色成对处理，区分普通表面、强调容器及其内容。局部反色区域也有成套对应角色。CSS custom properties 允许在组件中保持角色，而由主题改变取值。

**转化为样张：** 模板为主操作、柔和选中面、强色区分别给出前景/背景；局部主题可作用于一个容器。可复制的最小实现同时带上配对使用例，而不是让调用者复制色号后自行猜用途。

**边界：** 不要求引入 Material 组件、生成库或整套 token 命名。项目已有变量应就地映射，不能仅为使用模板建立第二套重复设计系统。

## 3. Carbon：深浅主题的层级逻辑不同

来源：[Color overview](https://www.carbondesignsystem.com/building-blocks/foundations/color/overview)。页面显示更新日期 2026-09-25。

Carbon 把 token 的用途与主题取值分开；主题变化保留角色含义。其浅色主题通过白与浅灰交替形成层级，深色主题逐层变亮。需要局部强反差时可用 inverse 角色或区域主题，而不是只翻转背景色。

**转化为样张：** 深色方向单独确定背景、表面、输入、边界和文字。增加“浅内容面 + 深品牌区”或反向组合，展示面积和区域关系的差异。保留同内容比较，避免把换布局误当作配色收益。

**边界：** Carbon 的灰阶及其叠层规则服务于 Carbon；不把“必须逐层变亮”写成所有界面的硬约束，不把品牌蓝视为通用最佳选择。

## 4. USWDS：主题、状态与底色分开管理

来源：[Theme color tokens](https://designsystem.digital.gov/design-tokens/color/theme-tokens/)、[State color tokens](https://designsystem.digital.gov/design-tokens/color/state-tokens/)。Theme 页列出的最近指导更新为 2024-05-15；其余以核查日为准。

USWDS 的项目主题从系统色中选出少量角色；状态另有信息、错误、警告、成功等角色。它允许不用的色阶不定义。主题页的 60/30/10 是对非底色部分的比例建议，页面也说明中性底色可能占主导。

**转化为样张：** 套装只覆盖样张真实使用的角色；主题强调与成功/警告等状态分开。每套附一句“大面积由谁承托、哪里强对比、哪里只点到为止”，让使用者理解色彩分布。

**边界：** 不引入统一 60/30/10 限额，也不把页面分成固定色块。既有品牌、图片和任务优先；色板条数不证明覆盖充分。

## 5. Atlassian：区别含义、强调与交互状态

来源：[Color](https://atlassian.design/foundations/color)、[Design tokens](https://atlassian.design/foundations/design-tokens)。页面未标明发布日期。

Atlassian 的颜色角色、强调程度和交互状态分别表达不同信息。品牌、成功、危险等角色不能因为色值接近就互相替代；无特定含义的 accent 可以换色而不改变体验含义。强底色上的 inverse 前景也要配对，黄色警告需要特定前景。

**转化为样张：** 同时显示品牌动作、持续选中、语义反馈，观察能否辨别它们。允许装饰或栏目辅助色带来丰富性，但不让主题绿色顺带把所有按钮当成“成功”，也不把整套警告色随品牌替换。

**边界：** 不复制完整企业级 token 分类。模板中的标签、文字或形状应补足含义；调色自由度不能只依赖色相区分。

## 6. W3C：检查实际配对，区分标准与审美

来源：WCAG 2.2 的 [1.4.3 文字对比说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[1.4.11 非文字对比说明](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)、[1.4.1 颜色使用说明](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)。这些是理解文档；规范性要求以其链接的成功准则为准。

普通文字与背景至少 4.5:1，大字至少 3:1；识别控件和状态所必需的视觉信息与相邻色至少 3:1，适用例外须分别判断。不是所有装饰边线都需要达标；不同非相邻状态之间也不要求一律 3:1。颜色不应是唯一的信息线索。

**转化为验收：** 按样张中实际使用的文字/表面、按钮/文字、输入边界和焦点/邻接表面计算；状态同时有文字或图形标记。实测透明合成后的颜色，不把各孤立色值的检测当成整页结论。

**边界：** 阈值通过只解决可见性的一部分，不是审美评分或完整无障碍认证。很细的线和轻字仍需看实际画面；不能为通过数字而加重全部分隔线。

## 本轮建议采用的实现取舍（本项目推演）

下列为基于上述方法与用户缺口的设计建议，不是任何来源规定的统一流程。

1. **用成套关系扩展选择。** 既有三方向外，优先补暖浅底与浓色、彩色主表面、深暖色、冷暖双色和局部反色等真正不同的组合；让每套同时决定底调、色彩分布和表面角色，避免仅替换按钮色。
2. **在共同内容中比较，再看对应场景。** 固定内容/基本布局用于分辨配色差异；另用阅读/展示/操作等简短场景检查搭配是否承托内容。无需另开多轮独立生成实验。
3. **导出可用起点。** 每套提供完整角色值、简短的应用示例和适用/冲突说明。既有项目选择性映射；未使用的角色无需预先增加。
4. **保留品味与决策空间。** 不把场景行业绑定色相，不要求每次让用户挑多套，不把示例视为唯一风格。若已有方向成立，直接沿用；需要新方向时才查样张。
5. **验证具体组合。** 检查整页与小界面、长中文和真实状态、深浅强表面邻接、重点配对对比及窄屏；结果只描述实际看过的方案和条件。

所有拟加入 runtime 的方法可压缩为入口、模板使用说明及少量差异提示。详细来源留在此维护记录，避免主技能反复加载外部系统概论。
