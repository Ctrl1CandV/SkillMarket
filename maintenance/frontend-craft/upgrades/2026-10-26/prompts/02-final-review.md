# Codex 独立终审提示词：判断本轮是否可以结束

请在新的会话中执行本提示词。你是这轮升级的独立审查者，审查 Ctrl1CandV/SkillMarket 的 frontend-craft 与 product-design 联合升级。不要以执行者“已经完成”的结论作为证据；也不要先阅读上一轮执行聊天中的自我评价。

用户会提供仓库、交付包解压目录、本轮维护目录和 execution-report 的位置。你可以读文件、运行已有项目、打开截图与进行必要检查；本任务默认产出审查报告，不直接修改技能来帮助它通过，不自动推送、合并、发布或移除 rc 标记。发现问题应先记录，后续修复另交执行者。

## 1. 确定审查依据

读取适用的仓库 README/AGENTS、原始 PLAN.md、REQUIREMENTS.md、ACCEPTANCE.md、交付 manifest 和基线版本；再看实际改动与执行报告。若当前验收文件与交付原版不同，先说明变化、理由及是否经过用户明确调整，防止通过降低门槛宣布结束。

本轮核心目标是：

- 产品依据能转成具体可见、可操作的界面关系。
- 排版覆盖整屏构图、文字体量、主次比例、密度节奏与响应关系。
- 视觉样式包括文字、颜色、表面、素材、状态的共同作用。
- 参考和样张具有实际可用的内容及诚实证据，能帮助执行而非形成另一套固定模板。
- 旧规则有适用条件，通用能力与已有有效判断被保留。
- 最终效果靠实际画面与使用验证；维护流程不成为日常 skill 的负担。

阅读和论文证据核对是主要观察场景，密集操作和内容展示检验通用性。无需评判用户尚未要求的全平台业务、商业化或完整品牌体系。

## 2. 先核对证据是否存在

核对运行版本与基线：原基线为 d4c9eadcaa8f7ba287c3cd7f61a26775552eaf11，frontend-craft 0.4.2、product-design 0.1.0；交付候选最初为 0.5.0-rc.1、0.2.0-rc.1，后续实际修订应有记录。

打开 evidence/manifest.json 引用的文件，抽查或完整检查关键原始产物。证据位置存在、文件格式正确、内容与报告相符，是进一步判断的前提。以下均不能代替实际证据：

- 技能提到了某个原则；
- 文档更完整或规则数量更多；
- 构建、JS 语法或静态工具返回成功；
- 截图文件生成、模型文字说“已看图”；
- 来源知名、star 很多或作者自称效果更好；
- 数字评分很高但没有可定位画面和行为依据。

没有浏览器/图像能力时，可完成静态审查但应明确整体效果无法终审。不要依据代码想象出画面，也不要用自己新做的示意图当作被审产物。

## 3. 分层审查

### A. 文件、规则与分工

检查 R01–R23、R31、R35 的实际内容与改动。重点找：

- 产品分析仍停在说明，关键取舍不能对应到页面区域或行为；
- “重要就置顶、标签都弱化、重复一律删除、阅读所有区域都松、状态分组永远优先”等绝对规则换个说法继续存在；
- 一页就跳过产品分析、多个页面就强制分析，或按技能不存在的固定路径调用；
- 主技能过长、所有 references 每次必读、固定多套候选/用户偏好审批/完整 PRD；
- 精修完全禁止必要空间联动，或反过来默认扩大到主结构重做；
- 真实内容、访问语义、状态反馈或素材事实被当成冗余删去；
- 代表性页面被当作全部范围交付，或普通颜色问题导致两技能无限互推；
- runtime 混入维护材料，覆盖用户后续有效改动，或未经授权安装、推送、发布。

上下文成立时可以保留已有关系，不能要求每次分析都有画面改动。

### B. 外部参考与样张资源

核对 candidate/documented/verified_visual 与实际事实相符。对于计入 release 覆盖的每条外部案例，实际查看保存的画面与原始来源，核对发布主体、日期、视口、状态、截图路径、使用依据、观察关系和迁移限制。不能把同一主体子域算多个独立来源，不能把原创样张或生成图算成熟外部案例。

检查阅读/核验、密集操作、内容展示三类任务覆盖是否真实，至少两个实际独立发布主体。方法文章或局部组件图可以补充，不能单凭命名覆盖完整任务。

打开 style-lab，实际查看三主题与其主要视图；执行主题/视图切换、过滤、引用往返、临时批注及组件状态。检查宽屏与窄屏、长中文与混排、实际字体、页面溢出、键盘焦点和组合状态。颜色角色静态合规不代表整页舒适；使用原始截图或重新运行判断。

### C. 新旧比较的公平性

读取原始 brief/data 与运行清单；确认两个版本在相同模型、工具、依赖、预算、数据、视口及功能范围下独立完成。确认构建者没有收到升级诊断、验收答案、另一版本代码或完整升级聊天。

查看全部尝试，不能只看精选结果。原版资源出错、某版本缺能力、重跑次数不同、截图状态不同或额外人工指导，都应评估其影响。重大不对称使效果比较无法成立，应列为缺证而非判新版更好。

若可盲化，先独立记录 A/B 观察，再查看版本映射与执行者比较结论。若文件或界面已泄露版本身份，诚实说明盲化局限，不声称双盲或用户研究。

### D. 目标效果与行为

按 ACCEPTANCE 实际查看完整视口、实际显示尺寸及关键操作过程。对主要论文阅读/核验任务重点回答：

1. 正文、解释、原始依据与操作是否形成清楚关系？证据定位和返回能否保留上下文？
2. 主体是否有适当空间？主从比例、连续面和疏密节奏是否相称？
3. 中文长标题、正文、引文、元信息、数字和工具文字是否共同形成可读层级？
4. 明暗、表面、边界与强调是否协调？变化是否超出了删内容和换按钮颜色？
5. 必需内容与功能是否保留，引用和数字是否准确，演示身份是否清楚？
6. 窄屏、焦点、选择、反馈和结果变化时是否仍成立？

密集操作与展示任务检查本轮规则引起的明显退化，例如都被套为阅读工作台、操作字段被删、作品被装饰框压小、所有页面只有同一种卡片和间距。

以 better/comparable/worse/unclear 加具体证据记录，不用一个平均分盖过关键问题。主要任务应有有意义的改善；差异模糊、原因不可判断或结果不稳定时，不能强行判升级成功。不要为了证明某版本更好修改原始任务。

## 4. 运行检查工具，但保持判断边界

可独立运行：

```sh
python3 <本轮维护目录>/tools/check_package.py --repo-root <仓库目录>
python3 <本轮维护目录>/tools/check_package.py --repo-root <仓库目录> --release
```

常规检查通过只说明结构。release 通过只说明资源字段和本地文件满足结构门槛，不能证明真的看过图片、来源使用条件真实、审美提升或行为正确。不修改检查器降低标准。

只有具体风险需要才追加验证；不要为每条文案建立测试或无穷扩大设备矩阵。能通过已有原始证据判断的，直接判断；仍存疑的指出最小补证。

## 5. 产出终审报告

写入本轮维护目录的 `reports/final-review.md`，并在回复中概括。报告必须包含：

1. **唯一主结论：PASS、NEED_FIX 或 INSUFFICIENT_EVIDENCE。**
2. 受审版本、相对基线、实际阅读/运行/查看的范围，以及工具或环境限制。
3. R01–R36 的结果和证据位置；可合并叙述，不能遗漏关键要求。
4. 主要阅读任务和另外两场景的对比判断、具体画面/操作依据与局限。
5. 已确认问题：严重性、文件/画面/操作定位、实际影响、最小修复。
6. 缺证项：缺什么、为什么影响结论、最小补证方式。
7. 非阻塞后续建议与本轮结束要求分开；不把全部偏好差异都设为阻塞。
8. 明确写出“本轮可以结束”或“本轮尚不能结束”，与主结论一致。

结论规则：

- PASS：关键要求已兑现；参考、样张、行为和公平使用比较证据充分；主要目标成立，其他场景无明显规则诱发退化；没有未解决的重要问题。结论仅限已测试范围，不承诺每次生成都更好。
- NEED_FIX：已有证据确认矛盾、错误声明、关键行为失败或明显退化。列出最小修复及需复测范围。若同时有缺证，主结论仍用 NEED_FIX，并另列缺证。
- INSUFFICIENT_EVIDENCE：尚无法可靠判断关键效果，例如真实画面未看、操作未执行、比较不公平、来源不可核对或结果不确定。即便没发现错误，也不能写 PASS。

不要将“已交付文件”写成“整轮优化已通过”，不要把未知当作合格，不降低原始验收要求来帮助执行者收尾。报告完成即结束这次审查，不自动修复、推送、合并或发布。
