## 输入与位置

用户会提供仓库目录和本交付包的解压目录；如果位于当前工作区，先查找确定。包内：

- `dev-only/maintenance/frontend-craft/upgrades/2026-10-26/`：计划、逐项要求、验收、来源、评测与工具，下称“本轮维护目录”。
- `baseline/`：提交 `d4c9eadcaa8f7ba287c3cd7f61a26775552eaf11` 的旧版两个技能。
- `manifest.json`、`SHA256SUMS`：交付清单和完整性记录。

先阅读仓库 README、适用的 AGENTS.md、工作区状态，以及本轮维护目录的 PLAN.md、REQUIREMENTS.md、ACCEPTANCE.md、DELIVERY_STATUS.md。不要臆造前文约定，也不要重新研究已经明确的全部问题。

## 目标与边界

目标是把产品依据转成可观察的界面关系，并让构图、文字、颜色、素材和行为共同改善最终画面。前面已经确认的缺失能力和旧规则修订都在 PLAN/REQUIREMENTS；以它们为完整范围。

两技能仍分别负责产品依据与页面设计，不新增第三技能、不要求两个执行 Agent 或额外交接审批。不要把通用技能改成论文平台固定布局。不要为了“看起来更专业”扩写完整 PRD、强制风格选择问卷、加入更多负面禁令，或把日常使用变成本轮升级的全部评测流程。

已有改写应作为起点。只为具体未兑现要求、实际缺陷或可观察效果问题修改；不要清空本包另写一套个人偏好的技能。重要内容保留并落实，不能通过缩短所有标题、删除证据或省略功能换取简洁截图。

## 1. 安全合并与记录

1. 读取 Git 状态，识别用户未提交改动。按实际情况在 dev 或由 dev 建立的隔离工作树工作，保留用户改动；不要强制 reset、清理或覆盖。

3. 当前仓库与包基线不同的文件先比较；保留后来有效改动，并记录合并判断。旧版离线快照放入独立评测目录，不能与新技能同名混装。
4. 运行静态工具，使用实际路径：
   `python3 <本轮维护目录>/tools/check_package.py --repo-root <仓库目录>`
5. 将执行记录和证据放在本轮维护目录下的 `evidence/`、`reports/`；原始截图保留原件。维护资源变多不应扩大日常 skill 加载范围。

## 2. 补全真实外部参考画面

先读实际仓库 `frontend-craft/references/` 中的 reference-selection.md、exemplars.md、exemplar-index.json，以及本轮维护目录中的 SOURCES.md。

当前索引有方法资料和继承候选，**没有 verified_visual 外部画面包**。Oil 说明沿用旧版，不能据此声称你已看过当前页面。优先查看任务相近、来源与使用条件明确的成熟开源产品、官方演示或原作者案例；可以替换不可用候选，记录理由即可。星数和安装量只辅助发现，不代表适用于本任务。

按 ACCEPTANCE 覆盖连续阅读/证据核对、密集工具操作、内容展示，至少两个实际独立的发布主体。数量由覆盖决定，避免堆砌相似图片。正文、工具和展示要看有内容的实际视口；营销页中嵌入的一张小图不能自动当作完整工作界面。

对每个计入覆盖的案例：

- 实际打开原页面或可靠原始图片；必要时运行开源项目的原有演示。确认截图确实对应来源、状态和内容，而不是生成或重画的近似界面。
- 保存有用的完整视口，按需要补局部或状态。保留真实尺寸；可复用截图放在 `frontend-craft/assets/references/<id>/`。
- 确认截图或所包含素材可按预期再分发，保留明确依据；公开可访问、代码开源并不自动证明全部品牌/图像素材同许可。无法确认的条目可只保留链接并标 candidate/documented，改选可用来源。尊重现有访问权限，不绕过登录或付费限制。
- 用可用图像/浏览器能力真正查看已保存的文件。记录它呈现的主次、密度、文字、色面和任务关系，说明能迁移什么、哪些内容/语言/设备条件不同。不要只有“简洁、高级、现代”。
- 不把测量推断写成官方 token，不将作者宣传或模型评审改称用户研究。

## 3. 实际运行样式样张

打开 `frontend-craft/assets/style-lab/index.html`，使用项目或环境已有浏览器能力；不更换整个技术栈。三主题为 neutral-cobalt、ink-cyan、paper-berry。

完成 ACCEPTANCE 中的宽屏、窄屏、实际尺寸和操作检查。三个主题都需实际查看；对相同内容比较主体、文字、表面、前景、边界、强调面积和组合状态，不能只检查按钮色值。

验证阅读/列表/组件切换、搜索筛选与清空、引用定位与返回、临时批注预览、表单验证以及手动反馈状态。核对实际字体和回退、长标题、键盘焦点、窄屏滚动和固定元素。样张的“当前页面临时预览”不能被改写成服务器保存成功。颜色对比计算是辅助，不等于整体好看。

发现问题先修最大且具体的关系，再复看受影响处。报告主题、浏览器、视口、状态、截图与操作结果；源码存在、JS 语法通过、截图生成都不能写成已视觉验收。

如果当前环境无法运行浏览器，尝试已有可用替代能力；仍不可用时保留完整待检查项和可复现命令，继续其他工作，最后结论只能说明缺证，不能造图代替。

## 4. 进行相同条件的新旧使用比较

这是验证技能能否改变产出的关键步骤；不能以阅读技能后的主观肯定代替。

原始任务位于 `evals/reading-evidence/`、`evals/dense-operations/`、`evals/public-exhibition/`。每组 brief.md 与 data.json 必须两边完全相同。所有数据为明确虚构样本，不可转述为真实科学或业务事实。

先建立运行清单，记录共同模型/版本、工具权限、工程起点、依赖、任务输入、数据校验值、视口、运行预算和尝试编号。旧版加载 baseline 中两技能，新版加载最终候选两技能；技能资源差异就是本次比较的变量。

为两边建立独立工作目录和新上下文。若宿主支持无历史子 Agent，使用不继承升级对话的方式；否则创建可供全新会话使用的最小任务包与启动提示，并明确仍待执行，不能在带着全部答案的上下文假装盲测。遵守现有项目与宿主规则，不为隔离而删除或篡改安全/权限指令。

**构建者只能得到：**

- 原始 brief.md 和 data.json；
- 指定版本的两个技能及其配套资源；
- 完全相同的工程约束、运行环境和任务范围。

不要给构建者 PLAN、REQUIREMENTS、验收答案、另一个版本产物、本轮诊断或任何预定布局与配色。允许按自己版本 skill 正常查询参考和自查，但两边工具和预算对等。不要让旧版多缺能力，也不要在新旧间复制代码。旧版资源不可访问时按实际情况记录，并判断是否造成不可比较，不悄悄删掉这一失败。

三个场景各完成一组配对实现；只有具体不确定性需要解决时才追加。保存全部尝试，不挑选每边最好结果。每个任务在 1440 × 1000 与 390 × 844 CSS px 的相同内容和状态下捕获；关键操作用步骤和结果记录，必要时保存短录屏或连续截图。

协调者可将产物随机标为 A/B，单独保存映射。独立评审先看原始任务、同条件截图和实际运行结果，记录 better/comparable/worse/unclear 及具体依据，再揭示版本。诚实说明盲化的局限，不把小样本写成统计证明。

重点核对产品决定是否兑现、整体主体与比例、中文文字系统、密度节奏、颜色与表面、内容完整、证据往返和窄屏过程。主要阅读任务需要有具体可描述的改善，其他两任务不能因新规则明显退化。若比较不公平或结果不清，保留证据并写明缺口。为具体失败修订技能后，重新运行受影响任务和必要回归；保留修订前结果，不写针对 fixture 的模板答案。

## 5. 整理并交给终审

最终再运行静态检查和资源门槛：

```sh
python3 <本轮维护目录>/tools/check_package.py --repo-root <仓库目录>
python3 <本轮维护目录>/tools/check_package.py --repo-root <仓库目录> --release
```

release 只检查资源证据结构，不能代替图像、许可事实、行为或整体效果判断。不改工具规则来掩盖失败。

生成以下实际文件：

1. `reports/execution-report.md`：基线、合并、重要改动、实际运行范围、结论与未解决问题。
2. `reports/requirements-status.md`：R01–R36 的 implemented/verified/blocked/not-applicable、实现位置与原始证据；区分写了规则和实际生效。
3. `evidence/manifest.json`：每项截图、运行产物和记录的实际相对路径、用途、环境/视口/主题/状态与时间；不得引用不存在的文件。
4. `reports/comparison-report.md`：全部配对运行、共同条件、评审观察、揭盲结果和局限；保留 A/B 映射与输入校验值。
5. `reports/static-check.json` 与 `reports/resource-check.json`：真实命令输出与退出码。
6. 只有存在无法完成的工作时，补 `reports/remaining-work.md`，写明确切缺口、原因和最小继续步骤；没有实际运行的子任务不能写“完成”。

更新实际资源状态与交付说明，维护相对链接。完成后停在可审查的候选版本，报告可供独立终审的位置；不要把自己作为最终审查者，不预先改成稳定版或发布。独立终审由 02-final-review.md 在新的上下文执行。
