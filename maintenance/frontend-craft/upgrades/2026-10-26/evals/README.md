# 相同任务的新旧技能比较

本目录提供原始任务与固定数据，用于检验两个 skill 的实际输出。它不提供预期布局、配色或标准答案。所有业务、研究和展品内容为虚构演示，不能当成真实研究或真实组织记录。

## 任务

| 目录 | 用户要完成的事 | 主要内容 |
| --- | --- | --- |
| reading-evidence | 阅读论文样本，核对解释与原始依据，保留阅读和笔记上下文 | 长标题、摘要、正文片段、引用关系、证据限制 |
| dense-operations | 查找、比较、处理一批对象，并准确理解状态和结果 | 多字段、长名称、多状态、筛选与批处理 |
| public-exhibition | 浏览和理解作品，查看大图，选择参观场次并完成演示预约 | 原创虚构展品、同批 SVG 素材、作品叙述与预约规则 |

每个目录含 brief.md 与 data.json。SVG 只是 fixture 的作品内容，不是界面模板或成熟视觉参考。旧、新版使用完全相同的数据字节，不按某一版需要删减字段或换素材。

## 协调者的职责

1. 先读本轮 ACCEPTANCE 和执行提示词，固定共同模型、工具、工程条件、运行预算及视口。
2. 准备两套独立技能资源：旧版来自包内 baseline，候选来自最终 runtime/仓库文件。
3. 对每组任务建立两个独立工作目录和新上下文；每位构建者只收到下述最小输入。
4. 两边允许相等的正常实现、自查与修订机会。版本配套资源可以不同，这是被比较的变量。
5. 收集全部输出，使用相同内容与状态生成画面，并运行任务所需行为。不要只挑每边最好的一次。
6. 对评审者使用中性 A/B 标识，先观察再揭示映射；说明任何无法盲化或条件不同的地方。
7. 记录证据路径和局限。只有具体问题需要时追加运行，不用增加任务数量掩盖问题。

## 给单个构建者的启动文字

下面文字由协调者填入实际路径。两边文字保持相同，仅“技能版本目录”和工作目录各自不同。不要把本文件其余部分、升级 PLAN/REQUIREMENTS、评审答案或另一版本产物放入构建者上下文。

> 请读取指定目录中的 product-design 和 frontend-craft 两个技能，按其分工完成原始任务。任务说明在所提供的 brief.md，数据在 data.json。使用给定工程起点和共同技术约束，完成可运行的前端与任务要求的本地行为，正常检查并修复自己的实现。样本数据不属于真实业务，按任务要求标明演示性质。交付启动方式、实际实现范围和实际做过的检查。不要访问另一工作目录或请求另一实现的结果。

附上实际技能目录、brief、data、工作目录、工程约束和预算。这里不规定最终应有几栏、多少卡片、哪种强调色或具体布局。

## 不支持新上下文时

可以先准备最小运行包与启动提示供独立会话执行；记录为待运行。不要在已经知道本轮诊断和预期答案的上下文中完成两份实现后，声称是独立比较。既有项目与宿主的权限、安全规则继续有效，不为隔离而删除这些规则。

## 结果保存

原始实现、截图和操作证据保存在本轮维护目录的 evidence 下；reports/comparison-report.md 记录共同条件与具体观察。不要把结果写回这些原始 brief 或改掉数据以配合某一版产物。

评审方法与结束条件见上一级 [ACCEPTANCE.md](../ACCEPTANCE.md)。本目录本身没有任何“新版已经更好”的结果。
