# frontend-craft 0.4.2：白绿趋同与管理页问题拆解

2026-10-25。分析对象为当前工作区 `frontend-craft/` 的 0.4.2，配套 `product-design/` 为 0.1.0。安装目录的 0.4.1 不作为本轮结论的主依据。本轮不修改运行技能，以便区分现有规则、执行偏差和反馈后的页面修订。

## 结论

**0.4.2 没有把白绿写死。它也没有规定所有管理页必须低饱和、浅底或小面积强调色。** 但这不等于它已经能够稳定打破风格重复：当前文件比较擅长解释什么关系应当成立，选出具体视觉方向和把规则落实到页面仍很依赖执行者。本次旧管理页既暴露了这种可靠性问题，也存在明确违反现有规则的实现偏差。

不能把这次问题归咎于用户调用了旧版本，也不能仅凭一次新 demo 就声称 0.4.2 的问题已经解决。

**后续用户评价：** 用户查看本目录的新管理页后认为效果比原管理页更差，要求先提交两个技能的当前版本，待其阅读报告并给出思路再优化。因此，新稿没有证明改进有效；下文中的检查结果与成因推断不能替代用户对画面的评价。

## 1. 当前技能怎样工作

它是一组自然语言设计指令，不是包含默认主题的组件库。运行目录由入口和七份参考组成，没有一个自动给页面注入绿色的 CSS 模板。

| 文件 | 负责的决定 | 与这次问题的关系 |
| --- | --- | --- |
| `SKILL.md` | 范围、产品依据、内容、构图、实现、看图修订 | 能决定先处理什么，但不能代替实际设计与复看 |
| `references/content.md` | 对象、判断依据、操作与辅助说明 | 要求首屏优先当前对象与操作 |
| `references/layout.md` | 分栏、比例、密度、响应式 | 有三栏工作区代码起点，但注明不是固定模板 |
| `references/cjk-typography.md` | 中文字体、字号、断行 | 不支持用极小中文来制造精致感 |
| `references/visual-style.md` | 字体、色彩、图形、表面与状态 | 真正控制视觉方向的主要参考 |
| `references/exemplars.md`、`scenarios.md` | 范例关系与场景提示 | 工具参考偏重结构、操作和密度，非完整视觉样式样本库 |
| `references/review.md` | 画面与操作复看 | 明确静态检查不能证明视觉质量 |

入口要求整页新建先读视觉样式、中文页面读中文排版、实现后读看图清单。问题不能用“颜色参考本来就是可选的，所以不读也合理”来解释。

## 2. 颜色到底有没有写死

当前 `references/visual-style.md` 有直接的反证：

- 第 35 行：新方向从题材、素材和使用环境取色，不默认降低饱和度或套行业色板。
- 第 37 行：中性色可以保持中性、带共同色调，也可以形成冷暖对比；不强制全页统一染色。
- 第 39 行：方向开放时检查上一页的配色惯性，比较底调、明暗与主色面积。
- 第 41–48 行：冷白/钴蓝、墨色/冰青、浅粉/莓红、明黄/墨紫，是明确标注的假设搭配起点，不是固定色板。
- 第 60 行：工具可以保留鲜明的大色面，不限制固定颜色比例或色块数量。

因此，本次背景、绿色按钮、浅绿选中和灰绿文字的具体数值，都是实现时作出的选择，不是技能提供的默认变量。

## 3. 这次管理页实际采用了什么

旧文件：`../design-pair-2026-10-25/management.html`。以下来自源代码，不冒充本轮截图观察。

| 角色 | 实际颜色 |
| --- | --- |
| 页面底 | `#f4f4ef`，偏暖的浅灰 |
| 内容面 | `#fffefa`，近白米色 |
| 侧栏 | `#eeefea`，浅灰绿 |
| 主色 | `#28594b`，暗绿 |
| 选中浅底 | `#e7efea`，浅灰绿 |
| 次级文字 | `#77827b`，灰绿 |
| 边线 | `#e4e8e1`，很浅的灰绿 |

重复的并非只是“绿色按钮”，而是整套关系：**暖浅底、相近的浅表面、灰绿文字和边线、小块深绿强调。** 只替换按钮颜色，会保留大部分相同观感。

同时，管理页的很多具体文字低于技能建议的尺度：队列标题、筛选、逐字稿、备注和表头里出现 9–11px。例如逐字稿正文为 10px，记录信息和筛选标签为 9px。0.4.2 的视觉样式第 24 行建议数据密集管理页界面文字从 13–14px 起步，第 30 行明确不能持续缩字来塞内容。`body` 写了 14px，并不能弥补子元素普遍覆盖成小字。

按声明色值计算，次级文字 `#77827b` 与纸面 `#fffefa` 的对比约为 3.95:1；条目信息 `#7c8880` 与同一纸面约为 3.66:1；详情标签 `#8a948d` 与详情底 `#fbfbf7` 约为 3.02:1。它们低于技能第 64 行规定的普通文字 4.5:1。这里是静态配对计算，未声称测量了浏览器最终合成画面。

首屏还把统计卡、待办摘要和介绍面板放在直接校对之前；主要编辑工作区需要再进入。这不是所有后台的共同错误，但与本页已设定的“处理待校对录音”任务有距离。小字、接近的表面、分散的区块和缺少突出工作对象叠加，可能造成细碎、层级偏弱的观感。这是基于源码的诊断，仍需实际画面核对，不能把所有观感问题归于色相。

## 4. 为什么连续出现相似风格

### 已有证据

旧任务样例 `../current-skill-showcase-2026-10-25/tasks.html` 已采用相似组合：页面底 `#f3f6f2`、主色 `#2b6348`、浅绿 `#e8f1e8`、灰绿文字 `#66736a`。本次制作前读取过这个样例的源码。数值并非逐字复制，但它确实是上下文中现成的视觉参照。

历史评审也已记录任务、城市杂志、灯具三页配色相似。后来添加四种假设搭配起点和配色惯性提醒，但维护记录明确说明：新增规则的实际生成效果尚未单独验证。

这里要区分色相与整体底调：城市杂志主要强调色是铁锈红，灯具是陶土橙，音乐页则用了紫色和荧光黄。不能把这些页面都称为绿色主题；更广泛的共同点是近白或米纸底、带色的灰与柔和边线。management 与 tasks 的绿白角色组合相似，是其中证据最直接的一组。

这次制作时，我主动把管理页和艺术页设为同一虚构品牌，并继续选择绿色；“用户已经认可这个后台的绿白品牌”并不是既有约束。共享品牌可以解释部分一致性，却不能为不佳的字级和底色关系提供依据。

### 可以作出的推断

现成样例和先选定的虚构品牌，可能使后续实现倾向沿用已有组合；现有制作记录中未见与 0.4.2 反惯性提醒对应的可核对配色比较。这是有上下文证据支持的机制解释，不能据此断言所有使用该技能的模型都必然偏好绿色。

### 历史规则仅作背景

归档的 0.3.3 曾明确要求低饱和、大面积浅色、侧栏中性、主色只占中小面积，并给出完整 OKLCH 变量代码。**它的示例主色相为 250，并不是绿色。** 它固化的是柔和浅色的配方，而不是绿这一色相。

这些规定已从当前版本删除，不能说它们仍在 0.4.2 内直接生效。它们只解释旧产物为什么可能形成这类风格，以及为什么仅删掉旧规则不等于已经验证新行为。

## 5. 0.4.2 本身的不足与本次执行错误

| 判断 | 类型 | 依据与边界 |
| --- | --- | --- |
| 方向选择的可核对性不足 | 当前技能的可靠性风险 | 有“从题材取色”“比较底调”等要求，但执行者仍容易用泛泛理由宣布方向已明确；并非完全没有选择流程 |
| 允许更多风格不等于生成更多风格 | 当前技能的可靠性风险 | 四组候选是文字假设，不是已验证能稳定迁移的完整实例；不能把枚举色名当效果证明 |
| 工具范例多解释分栏、密度、状态，样式组合示范相对少 | 当前参考的覆盖局限 | 易于学到操作骨架，具体字级、表面和视觉重量仍需自行解决；这不是白绿硬编码的证据 |
| 0.4.2 的主要增量不在配色机制 | 版本事实 | 相比前版，重点新增 product-design 衔接、代表性内容与跨页上下文检查；颜色小节保持不变 |
| 将自选品牌方向当成继续沿用的依据 | 本次执行选择 | 统一品牌是我提出的，不是用户要求所有示例继承绿白 |
| 9–11px 操作文字、逐字稿 10px | 实现中的可读性风险 | 显著低于技能建议的字号起点；起点并非硬性最小字号，源码也不能证明曾持续缩字 |
| 多处普通文字配对低于 4.5:1 | 明确的实现偏差 | 与技能规定的普通文字对比要求不符，数值见前文 |
| 没完成实际画面复看 | 明确的验证缺口 | 旧页只做过静态检查；不能用语法、链接通过替代审美判断 |

product-design 能帮助确认“谁要看什么、如何完成任务”，但不会自动产出好的色彩、字体和空间关系。两个 skill 的衔接改善了设计输入，不代表页面设计和验证环节已经足够可靠。

若继续修改技能，值得优先处理的不是再增加颜色名称，而是以下环节：

1. 区分用户认可的视觉身份与执行者临时提出的方向；后者不能自动升级成下一页必须继承的品牌约束。
2. 让关键样式决定可核对：当前对象的尺度、底面分工、主要明暗反差、颜色面积和操作强调如何支持当前任务。只在确有分歧或发现重复惯性时比较方案，不要求每次生产固定数量的候选。
3. 补充表达差异明确、经过实际查看的工具界面参考，说明文字尺度、表面与控制区怎样共同成立，而不只展示分栏结构或色名。
4. 把可读性检查与视觉评价分开：字号和实际前背景配对可以拦住本次这类基础错误；画面是否有节奏、是否相称仍须真实复看。保留同一任务的反馈记录，不能用文档符合规范或单页获赞来宣称泛化提升。

## 6. 艺术页的反例说明什么

用户认可的 `river-archive.html` 也用了绿色：深青绿 `#193a36`、暖纸底 `#f0ede3`，同时有陶土/铜色、主视觉图形和显著的大标题尺度。它与管理页不是同一种颜色面积和层级关系。

因此，现有反馈支持优先检查“浅底、灰绿、小字、细线、小强调”这一组合及其任务适配，不能推导成用户讨厌所有绿色。把绿色禁掉或强制下一页用蓝色，可能只是换一种重复。

## 7. 本轮修订样例的解释范围

`management.html` 使用本工作区 0.4.2 与 product-design 0.1.0，由主执行者在当前对话上下文重新实现；它获得了本次用户反馈和明确的字号、任务重点要求。具体决定见 `design-notes.md`。

它是反馈后的修订样例，不是旧/新版本的受控对照。新页面若更好，不能把全部收益归因于技能版本；反馈、执行者、内容组织与具体设计选择均有变化。

优先检查：当前录音与待确认内容是否先进入视线；主要中文是否可以正常阅读；背景、正文、选择与动作是否各有清楚分工；搜索、编辑、保存、复核之间是否保持同一个对象。是否好看仍以实际画面和用户反馈判断。

本轮没有运行浏览器视觉验收。此前本地 file URL 的浏览器访问被工具策略拒绝，未通过其他入口绕过。静态代码和可独立验证的状态检查，不视为视觉验收。
