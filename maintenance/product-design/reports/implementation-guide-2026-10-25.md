## 1. 本轮目标与实施前提

### 1.1 要完成的工作

在现有 frontend-craft 之上，新增一个暂名为 `product-design` 的 Skill，用于网站、软件和平台的从零设计，以及已有产品的整体重设计或跨页面体验优化。同时小幅调整 frontend-craft，使它能够读取并贯彻项目的产品与体验设计依据。

新 Skill 应帮助 Agent 理解产品价值、用户当前任务、核心内容和流程，并据此决定展示重点、页面职责、信息组织与整体表现方向。frontend-craft 继续负责把这些决定做成具有良好视觉、交互和细节的界面。

本轮默认采用两个 Skill 的组织方式，暂不新增 Plugin。若工作区已经存在同名或职责重叠的 Skill，应先核对并复用；不能仅因本文用了一个名字就重复创建。

### 1.2 当前问题与判断的边界

用户在理想化展示任务中反复打磨 frontend-craft，但把它用于真实平台建设后，仍认为结果普通。用户指出：真实页面需要承载功能和内容，设计质量依赖对整个平台价值、主次关系和用户任务的理解。工业管理平台、鲜花商店与演唱会售票平台，可能需要截然不同的视觉重点。

本轮接受这一方向作为需要补充的能力：让设计方法在真实产品约束下发挥作用。当前指导不声称已经证明某次页面效果不佳的唯一原因；具体结果仍需结合真实页面和执行过程判断。

此前关于前景背景配对、样式协调、中文排版、视觉复核等改进继续有效。新增工作流需要把这些能力放到合适的产品情境中使用。

### 1.3 以本地现状为实施依据

用户明确说明最新修改在本地。执行 Agent 应先读取本地 `AGENTS.md`、仓库约定、当前分支、工作区改动，以及 frontend-craft 的现有正文和相关参考。不要用远端旧版本覆盖本地更新，也不要假定本文件撰写时掌握了最新完整目录。

本文中的文件名是建议映射；以本地真实结构为准。已有成熟指令应合并和复用。版本、索引、发布范围、维护材料位置和提交方式遵循现行仓库约定。不要因为外部 Skill 的模板而恢复本仓库已移除的宿主适配文件、安装入口或 Plugin 清单。

本文较长，是为了说明思想、参考和实施取舍。实施时应提炼为简短的运行指令与少量按需参考，避免把全文复制进 `SKILL.md`。

## 2. 指导思想：产品理解怎样进入视觉设计

### 2.1 理解产品，会改变画面本身

产品价值、用户任务、实际内容和视觉设计之间存在连续关系：用户为什么来，决定需要看到什么；内容之间的关系，影响如何排列；用户需要先注意什么，影响尺寸、对比、颜色和空间；使用节奏与品牌情绪，影响材质、图像和动效。

因此，新 Skill 的核心能力应是把产品理解转化为可执行的设计决定。单独写出用户画像、功能清单或产品定位，还不足以完成这项工作。

实施时，每一项重要分析都应能回答：它改变了哪个设计决定？例如“用户需要连续监测异常”应该影响状态的比较方式、异常的可见性和处理入口；“用户需要感受演出现场”应该影响素材选择、主视觉尺度和浏览节奏。

### 2.2 真实内容是设计输入

真实任务会带来长短不一的标题、不同数量的数据、缺失的素材、角色差异，以及进行中、失败和完成等状态。视觉方案应在这些条件下成立。

代表性内容应尽早进入设计。已有数据时使用实际或脱敏内容；没有数据时，使用符合真实长度、分布和状态的样本，并标明其为样本。不要为了展示整齐，悄悄缩短所有文案、删去必要字段或把复杂内容替换成三张等长卡片。

### 2.3 用户价值包含情绪与品牌体验

“服务用户”既包括快速操作、准确判断，也包括欣赏、期待、探索、信任与记忆。艺术展示、鲜花选择、文化活动等场景，可以把图像、色彩、排版张力和氛围作为核心体验。

新 Skill 不应把产品理解统一解释为减少装饰、降低饱和度或提高信息密度。它需要说明为什么某种表达对当前用户和内容合适，并允许富有表现力的方案。

### 2.4 依据具体任务，保持行业判断的弹性

行业提供线索，不能直接决定整站风格。相同鲜花商店中，浏览花束、选择配送日期和核对订单承担不同任务；相同工业产品中，实时监控、阅读报告和品牌介绍也可能有不同表达。

配色的来源也应区分：品牌识别、状态语义、数据分类、内容素材和情绪表达可能同时存在。多色花束照片可以提供主要色彩，周围界面仍可安静；演出主视觉可以强烈，选座与费用区域仍需清楚。不要形成“行业名称 → 固定色板或固定布局”的规则表。

### 2.5 设计过程需要反复校正

产品理解、视觉探索和实现应相互校正。先建立足以开始的理解，再通过真实内容和代表性实现发现遗漏；不要求所有分析完整结束后才能设计。

需要保留实际观看与操作的环节。合理的设计依据可以提高选择的针对性，但不能替代对画面和体验的检验。完成标准应同时考虑目标是否准确、任务是否顺畅、画面是否优秀，以及实现是否成立。

## 3. 两个 Skill 的职责和触发边界

### 3.1 能力划分

| 方面 | product-design | frontend-craft |
| --- | --- | --- |
| 主要职责 | 建立平台理解，组织跨页面体验，确定本次设计目标与变化范围 | 在具体任务和方向下完成页面、组件、视觉与交互细节 |
| 关键决定 | 核心对象、主要流程、页面职责、内容优先级、整体表现方向 | 页面构图、字体与颜色关系、材质、素材组织、控件与状态表现 |
| 产出 | 可持续读取的项目设计依据，以及能进入实现的设计决定 | 可查看和操作的界面，以及实际效果的修正 |
| 反馈责任 | 根据实际内容和实现结果修正产品与体验判断 | 发现跨页面冲突或不合理假设时反馈，并保留页面级自主判断 |

这是一种职责组织方式，不要求两个独立 Agent。一个 Agent 可以按需读取两个 Skill。两个 Skill 共同使用项目上下文，避免来回重新分析。

### 3.2 触发与范围判断

| 用户任务 | 建议处理 |
| --- | --- |
| 从零搭建有多个页面和核心流程的平台 | product-design 建立整体依据，再衔接 frontend-craft 落地 |
| 全面重设计已有平台，或调整核心流程、导航和页面关系 | product-design 先判断现状与变化范围，再实施 |
| 新增能力，明显影响多个页面、角色或核心对象 | 对受影响部分使用 product-design，复用其余已确认背景 |
| 已有明确设计依据，继续建设一组页面 | 读取依据后直接执行；不重复完整分析 |
| 做一个范围清楚的页面或组件 | frontend-craft 做必要的局部理解并完成任务 |
| 内容与结构固定，只优化视觉样式 | frontend-craft 保持范围，依据现有目的和素材调整 |
| 单纯调整文案、颜色、间距或修复局部缺陷 | 直接处理，不触发全平台设计流程 |
| 仅请求评审或设计说明 | 按用户要求交付诊断或方案；实现属于另一个交付范围 |

任务范围应根据实际变化决定，不能单凭“优化”“重新设计”几个词机械分流。一页也可能包含核心流程重构；很多页面也可能只是同一主题的样式调整。

### 3.3 frontend-craft 保留足够的设计能力

frontend-craft 仍应决定页面级内容组织、排版、文案呈现和交互细节。上游提供目标、依据、约束与关系，避免预先把每一个像素锁死。

product-design 对视觉方向作出有依据的约束，例如“设备状态需要可连续比较”“花束照片承担主要视觉表现”。具体构图、色彩配对和精修由 frontend-craft 继续解决，发现更合适的方案时可以反馈。

## 4. 值得借鉴的 Skill 与成熟设计实践

本节区分来源事实与本项目的转化建议。来源展示了已有方法，不构成其必然优于 frontend-craft 的效果证明。以下参考均查阅于 2026-10-25，链接与阅读位置见第 15 节。

### 4.1 Impeccable：产品事实与视觉决定分别保存

**来源事实：** `init.md` 先检查文档、功能、流程、路由、角色和资产，再补充重要信息，并维护 `PRODUCT.md`；`new-work.md` 区分产品事实、持久视觉决定和单个页面的设计依据，也区分扩展现有界面与建立新方向。[R01][r01] [R02][r02]

**本项目的转化建议：** 将通用方法留在 Skill，将具体产品的目标、约束和已确认选择留在项目内。后续优化直接读取并更新这份依据。新建、扩展和重设计需要不同起点。

不照搬其固定确认轮次、候选抽取机制或文件拆分数量。对用户已明确的目标继续执行；对本项目而言，一份简短文档通常可以承载初版上下文。

### 4.2 Oil UI：让参考和题材进入实际设计方向

**来源事实：** Oil UI 从用户、主要任务、真实内容和设备确定范围；设计方向参考要求结合当前产品的内容、受众、使用场合和真实参考画面，形成具体选择。[R03][r03] [R04][r04]

**本项目的转化建议：** 要求 Agent 说明参考中的哪种内容关系、视觉重点或表现手段适合当前产品，并落实到界面。方向描述应能够影响构图、素材、排版或配色。

不继承固定候选数量、默认展示页、风格禁令、强制动效或固定色彩比例。引用外部方法时，保留它解决的问题，重新判断其限制是否适合本仓库。

### 4.3 Carbon：根据当前任务组织 productive 与 expressive 表达

**来源事实：** Carbon 的 Typography 文档区分面向操作的 productive 和面向阅读、探索的 expressive 排版，并允许混合。其官方示例包括：网站的菜单、搜索和筛选使用紧凑排版；开户页面的说明区与表单使用不同表达。[R05][r05]

**本项目的转化建议：** 把“当前区域承担什么体验”写进设计依据。整站可以有统一品牌，而不同页面或区域使用合适的尺度与节奏。

这个案例直接支持本轮的核心思路：用户任务可以改变视觉语言。借鉴其判断方法，不把 IBM 的字族、字号、组件或整体风格变成所有项目的默认值。

### 4.4 Carbon：状态表现由用户需要关注的程度决定

**来源事实：** Carbon 的状态指示模式按情境与关注程度组织状态表达，并结合颜色、形状、符号或文字帮助识别。[R06][r06]

**本项目的转化建议：** 对监控、管理、任务处理等界面，先确定哪些状态需要立即行动、哪些只需查阅，再分配视觉强调。不能把每个状态都做成同样醒目的彩色标签。

本方法不等于“工业平台只能素色”。真实业务语义和既有约定优先于外部系统的具体色值或状态命名。

### 4.5 Shopify：商品媒体同时承担展示和理解任务

**来源事实：** Shopify 将图片、视频和 3D 模型作为帮助理解商品的媒体。其媒体交互指南同时处理控件识别、与主题的一致性、主次操作竞争，以及播放和导航行为。[R07][r07] [R08][r08]

**本项目的转化建议：** 对鲜花或演出等依赖视觉内容的产品，先明确素材需要让用户理解和感受什么，再安排展示面积、裁切、浏览方式与行动入口。

“绚丽”可以主要来自内容本身，也可以来自与内容相呼应的页面表达。缺少关键素材时应显式记录；不能用随意渐变或装饰卡片替代真正需要展示的对象，并宣布效果已完成。

### 4.6 Design Council 与 GOV.UK：先理解问题，并在实现中继续学习

**来源事实：** Double Diamond 包含理解问题、定义方向、发展方案和小规模检验，并明确过程会迭代。GOV.UK discovery 强调用户目标、完整旅程和实际约束。[R09][r09] [R10][r10]

**本项目的转化建议：** 使用简短的探索与收敛过程，优先解决会改变设计的重要未知，再通过代表性流程检验。工作量随任务复杂度调整。

不照搬机构流程的周期、组织结构或审批方式。对个人项目和 Agent 工作流，应尽量减少重复访谈和形式化文件。

### 4.7 Anthropic Skill 编写实践：让知识变成可执行流程

**来源事实：** 官方指南建议通过清晰工作流、条件分支、反馈循环和按需参考组织复杂任务，也强调用真实使用检验 Skill。[R11][r11]

**本项目的转化建议：** 主文件保留路由、关键判断和交接要求；具体分支与示例按需读取。验收关注 Agent 是否据此作出正确行动，不以文档变长或自评良好作为证据。

## 5. product-design 的完整工作流

### 5.1 确定范围并复用已知信息

先判断本次交付是评审、设计方案、局部实现还是完整建设；识别已有设计依据和用户已经确认的方向。范围明确时直接进入相关部分。

开始时应能用简短语言说明：本次处理哪个产品或子系统、主要任务是什么、可以改变哪些内容。不要把每次调用都变成一次完整产品访谈。

### 5.2 建立足够的产品理解

先从现有材料获取证据，再补充询问。阅读顺序以发现决策所需信息为目的：

1. 查看产品说明、用户原话和已有设计决定，理解目标与取舍。
2. 粗看页面、路由、核心对象和角色，建立整体关系。
3. 走查与本次任务相关的真实流程；有运行环境时实际查看和操作。
4. 查明涉及的能力、状态和工程约束，区分已实现、计划中和推断内容。
5. 仅对会显著改变方案、且现有材料无法回答的问题提问。

建设者的偏好、最终使用者的需要、当前代码的事实应分别记录。当前页面存在一个功能，不代表用户认可它的优先级；代码中有一种颜色，也不代表它是不可改变的品牌资产。

没有真实访谈时，不能制造画像、调研结论或用户行为数据。可以基于任务作有限假设，标明依据和可能影响。可逆细节自行决定；会改变主要任务或已有承诺的分歧才需要用户澄清。

### 5.3 明确核心对象、任务与页面职责

建立能够解释产品的整体模型：主要对象是什么、对象之间是什么关系、用户怎样从进入到取得结果，以及结果如何被继续使用。

对相关页面写出其主要职责：用户在这里需要看见什么、判断什么、做什么，操作后到哪里。区分入口、主工作区、详细查看、配置和结果等职责，但不要求每一种职责都创建独立页面。

根据真实任务安排导航和内容，避免直接把后端接口、数据库表或功能目录逐项变成菜单。相同功能在流程中的位置不同，界面表现也可能不同。

能力是否存在、入口放在哪里、什么时候突出展示，应分别判断。必要功能需要保留，但不必全部同时占据首页或主工作区。

### 5.4 形成内容与视觉方向

在决定主视觉或色板前，先确定当前页面的主要内容、主动作或主要体验，以及支持它们的信息。明确哪些对象应该先被看见，哪些内容需要同时比较，哪些只在相关时出现。

随后结合品牌、素材、使用节奏和参考，确定表现方向。方向应具体到能影响实现，但保留设计空间：例如异常与正常状态的视觉差异、花束摄影与界面底色的关系、演出素材与购票入口的关系。

此阶段调用或读取 frontend-craft 的相关设计能力。产品理解与视觉判断可以交替进行；看到真实内容后发现方向不成立，应及时调整。

### 5.5 完成代表性的真实体验

选择一条足以体现主要价值和关键约束的任务流程。本次交付包含实现时，先在真实项目中完成其必要页面、内容和状态；仅请求评审或设计时，交付对应的诊断、方案或用户要求的原型。范围由任务和待验证问题决定，不固定为首页、三张卡片或若干风格 Demo。

已有真实工程时优先复用工程与组件。只在需要隔离不确定问题或用户要求原型时创建独立原型，并说明原型与最终实现之间的差距。

存在实际方向分歧时，可以用最小必要的候选帮助判断。方向已经明确时直接深化；不把多方案展示作为必经步骤。

### 5.6 查看结果，修正后扩展

检查用户任务、内容关系、视觉效果和实现状态。根据证据修正原因所在的层面：目标理解有误则更新依据，结构不顺则调整流程，画面普通则继续改善视觉选择，实现失真则修复具体实现。

有效的关系再扩展到其他页面。共享组件和视觉规则要统一，但页面职责不同，可以保留合适的密度与节奏。

没有查看画面或操作条件时，可以完成能够验证的部分，但应明确区分“已实现”“已静态检查”“已视觉查看”和“已实际操作”。

## 6. 从产品事实到页面表现的转化方法

这一部分是新 Skill 应重点提供的判断方法。目标是使产品分析实际改变前端，而不是增加一份独立于页面的报告。

| 已知信息 | 需要作出的设计判断 | 对界面的可能影响 | 如何检验 |
| --- | --- | --- | --- |
| 用户需要连续发现异常 | 什么值得立即注意，什么保持背景地位 | 状态对比、排序、异常附近的处理入口 | 在正常与异常混合内容中能否发现并处理问题 |
| 用户需要比较相似对象 | 哪些属性必须并置 | 列表或表格关系、对齐、筛选与选择反馈 | 使用真实数量和差异能否完成比较 |
| 用户通过商品或作品产生兴趣 | 哪些素材最能呈现价值 | 图像尺度、裁切、版式节奏、背景与素材的色彩关系 | 主体是否明确，真实素材是否仍有表现力 |
| 用户需要理解复杂材料 | 哪些信息连续阅读，哪些按需展开 | 行长、层级、引用、旁注与导航 | 长内容是否仍可读、可回到上下文 |
| 用户进入确认或交易阶段 | 什么信息决定下一步，错误怎样恢复 | 表单分组、价格与状态可见性、主动作和反馈 | 是否能清楚判断并完成当前任务 |
| 产品需要表达特定情绪或品牌 | 情绪由什么内容和形式建立 | 字体性格、颜色、材质、图形和适当动效 | 用户能否感受到目标表达，操作是否仍成立 |

表中的“可能影响”是推理方向，不是强制版式。实施时根据当前产品证据选择。

### 6.1 给具体内容分配视觉地位

先区分主要任务对象、支持判断的信息、当前操作和次要工具。重要性可以来自使用频率、当前阶段、情绪价值或错误后果，不只由商业转化或点击频率决定。

形成方向时，应能指出真正的视觉重点。它可以是一组需要比较的数据、一件商品、一段正文或一个互动区域，不必总是一个大标题或单独按钮。

### 6.2 颜色由角色与内容共同决定

明确颜色承担的角色：品牌识别、状态区分、数据分类、内容呈现或氛围。再判断这些角色之间如何协调。

如果花束照片已经包含丰富颜色，界面可以通过底色和文字关系突出花束；如果主题活动需要强烈氛围，背景和图形也可以参与。选择依据是当前内容、品牌和任务，而非统一的色相数量、面积比例或饱和度上限。

需要同时承载状态与品牌的界面，应让两者含义清楚。不要因品牌喜欢红色，就使错误状态与普通装饰无法区分；也不要因为有错误状态，就禁用所有品牌红色。

### 6.3 功能密度与表现力可以共同成立

管理平台可以有精致的字体、清晰的空间秩序和可识别的品牌；展示网站也可以有高效、紧凑的筛选与结算区域。判断重点是每个区域承担的任务及其与整体的关系。

不要把高密度等同于粗糙，也不要把大留白等同于高级。真实内容数量、比较需要和使用距离会影响合适的选择。

### 6.4 把抽象要求改写为可执行决定

| 原始要求 | 需要补充的设计依据示例 |
| --- | --- |
| 平台看起来更专业 | 哪些任务需要可靠感；状态、层次、文案或细节中哪些部分目前削弱了它 |
| 花店更有吸引力 | 主打花束与购买场景；摄影是否足够好；页面怎样让用户看见花型、体量和搭配 |
| 演出页面更有冲击力 | 哪段舞台素材、艺术家形象或主题表达承担主视觉；购票信息在哪里保持清楚 |
| 工作台更简洁 | 用户真正需要持续看见什么；哪些重复说明或低频工具可以合理收起 |
| 全站更统一 | 哪些对象、状态、控件和品牌关系应一致；哪些页面需要保留自己的节奏 |

这些决定写入项目设计依据，随后在真实画面里检验。不要把推理过程直接转化成界面上的说明板块。

## 7. 新建与重设计的不同处理

### 7.1 从零搭建：围绕核心价值建立第一条完整流程

从零任务常有较多未知，应先确认产品服务的主要情境、核心对象和必要结果。把已明确需要的能力与仍待证明的想法分开，决定第一版的合理范围。

先组织最主要的使用过程，再确定页面和导航。需要的品牌、情绪和素材也应在这个阶段进入设计，避免功能框架做完后才临时补一层视觉风格。

在任务允许实现时，完成主要流程的必要部分，包括合适的进入方式、主要操作、结果和继续使用。相关的空状态、进行中、失败恢复等按真实需要纳入，不强制制造与产品无关的状态。

新建任务需要防止两种偏移：一是把未来所有功能都纳入第一版；二是为了尽快产出，套用与核心任务无关的欢迎页、数据卡片和功能介绍。应能说明每个主要区域对当前产品的贡献。

### 7.2 已有平台重设计：以现状与目标之间的差距确定变化

先查看当前界面和流程，记录用户认可的部分、实际问题以及本次希望获得的变化。可使用截图、操作记录或代码位置作为依据；没有用户研究数据时，不给推断加上“用户普遍认为”的表述。

把保留与可变内容具体化：品牌资产、核心任务、数据含义、既有交互习惯、工程约束、偶然形成的组件和样式默认值，不能笼统归为一类。

再判断问题需要在哪一层解决：

| 现象 | 优先检查的层面 | 对应改法 |
| --- | --- | --- |
| 核心任务被次要功能遮住 | 产品优先级、内容组织 | 调整入口、页面职责与呈现次序 |
| 页面之间重复录入或丢失上下文 | 流程与状态关系 | 处理跨页连续性和共享信息 |
| 内容合理但画面平庸 | 视觉方向、素材和具体关系 | 交由 frontend-craft 深化参考与完整视觉方案 |
| 同类控件各有样式 | 共享组件与设计规则 | 从共同实现或规则修正，而非逐页叠补丁 |
| 桌面截图尚可，真实内容下拥挤 | 内容与布局假设、响应式 | 使用代表性内容重新安排空间与状态 |

针对最能暴露问题的核心流程先实施，再检查共用组件和相邻页面的影响。大范围优化应覆盖重要关系，不必重写全部页面、替换框架或重做已经成立的品牌。

### 7.3 已有明确方向的继续建设

对继续建设的任务，先读取已确认依据，定位本次增加或改变的部分。只有目标、素材、流程或约束发生实质变化时，才重新讨论相应决定。

全站理解应随项目积累，避免每次调用重新从零分析。上下文过时或互相矛盾时，修正受影响的部分并保留变更理由。

## 8. 项目上下文与两个 Skill 的交接

### 8.1 在目标项目中保存依据

SkillMarket 保存可复用的方法；被设计的项目保存自身事实与决定。不得把某一个平台的具体导航、配色或用户偏好写成 product-design 的通用规则。

优先沿用项目已有产品或设计文档。没有合适位置且需要持续建设时，可建立一份简短 Markdown，例如项目约定目录中的 `design-context.md`。这里仅建议内容形态，不要求创建固定路径或额外文档体系。

已有 PRD、设计系统和任务说明分工清楚时，用短索引指向它们即可。避免复制后形成多个互相冲突的权威版本。

### 8.2 建议包含的信息

| 信息 | 应写清楚什么 |
| --- | --- |
| 产品与当前范围 | 平台的主要价值，本次涉及哪些部分，交付是方案还是实现 |
| 用户与主要任务 | 谁在什么情境下完成什么，什么结果表示完成 |
| 核心对象与流程 | 对象关系、必要页面、信息与状态如何流转 |
| 页面职责 | 各页面主要呈现什么，用户在这里判断或操作什么 |
| 保留与可变范围 | 用户确认的偏好、品牌与能力，允许重新考虑的默认值 |
| 内容和素材 | 已有内容、代表性样本、素材来源、重要缺口 |
| 视觉方向及依据 | 主体、层次、表现力度、品牌与语义色关系，以及参考中的具体借鉴 |
| 实现与检查重点 | 涉及的状态、设备或工程约束，首先实现哪条流程，如何判断结果 |
| 未确定内容 | 哪些是推断，影响什么，何时需要进一步判断 |

记录中应能区分用户已确认的要求、代码或运行结果中的事实，以及 Agent 的设计提议。重要决定附上简短依据或可定位的材料来源，无需为每个局部像素建立记录。

### 8.3 最小交接内容

交给 frontend-craft 时，至少应让它知道：

- 当前页面或流程服务的用户任务与完成标准。
- 真实内容、核心对象、必要状态和页面之间的关系。
- 需要保留的内容及本次允许改变的范围。
- 视觉重点、整体表现方向及其依据。
- 需要优先查看和验证的结果。

这些信息已经存在于当前上下文或项目文档时直接复用，不要求重新生成“交接包”。交接的完成标准是足以开始具体设计，并能指出尚未确定的问题。

### 8.4 反馈与退回的条件

frontend-craft 在实现中发现主要任务、内容关系或已确认约束相互冲突时，应修正对应设计依据，必要时向用户澄清。普通字体、空间、配色和组件细节由它继续解决。

例如，真实内容显示用户必须同时比较两个对象，但现有方案把它们放在两个互斥页面，这属于需要反馈的结构问题；某个按钮在选定背景上显得沉重，则先在局部视觉层面调整。

不使用两个 Skill 相互反复调用的循环。上下文已经足够时继续推进，只有新的事实或结果造成实质影响才重新进入相关判断。

### 8.5 缺少配套 Skill 或文件时

不要假设每个宿主都支持自动调用另一个 Skill，也不要在运行指令中硬编码一个必然存在的兄弟目录。

可用时按宿主机制读取相关 Skill；不可用时，利用已有上下文和项目规范完成当前范围内的工作。仅在必要信息确实缺失时补充判断或提问，不能因为缺少某个文件名就阻塞任务，也不擅自安装新的依赖。

## 9. 四个应用示例

本节是为说明方法构造的应用示例，不是对用户实际平台的审计，也不是已验证的成品。第 4 节中的 Carbon 官方界面案例和 Shopify 媒体规范是外部真实参考；以下内容是结合这些方法作出的项目化推演。

### 9.1 工业管理平台：围绕判断与处理组织视觉

**假设情境：** 值班人员需要观察设备状态，识别值得处理的异常，查看原因并记录处理结果。

设计应先查明：什么算异常、哪些状态需要立即行动、当前有哪些可靠数据、谁可以执行哪些操作。不得为展示完整而编造故障等级、处置能力或状态含义。

**可形成的决定：** 主区域支持状态比较和异常定位；处理入口靠近对应对象；相同状态在概览与详情中保持一致；背景和装饰的视觉力度要与状态识别相协调。

**交给 frontend-craft 的工作：** 使用真实数量和字段安排信息，协调状态、正文、控件和数据图形的轻重关系。品牌可以保留，重点是不会混淆状态含义。

**验证问题：** 正常与异常混合时，用户能否发现目标、理解原因并进入处理？页面是否清晰、精致且适合持续使用？

**参考方法：** Carbon 的状态语义与关注程度；具体业务定义仍由项目提供。[R06][r06]

### 9.2 鲜花商店：让花束和购买情境成为画面依据

**假设情境：** 用户希望为某种场合买花，需要判断外观、体量、价格和可配送条件。

设计先查看实际花束素材与商品差异。花束摄影、包装和使用场景可以承担主要情绪表达；界面可以丰富，也可以通过协调的底色衬托已经丰富的照片。

**可形成的决定：** 浏览时优先展示可比较的花束形态与价格；详情承担尺寸、搭配和配送判断；选择日期与确认订单时，让当前选择和必要条件易于核对。

**交给 frontend-craft 的工作：** 以实际照片决定裁切、比例、文字落点和色彩关系，保持花束主体完整。根据页面职责调整视觉节奏，不能让统一模板裁掉最重要的商品特征。

**验证问题：** 用户能否分辨商品差异并完成选择？替换为真实照片和长商品名后，页面是否仍然成立？素材不足时哪些视觉目标尚未完成？

**参考方法：** Shopify 把商品媒体作为理解与展示商品的组成部分；鲜花场景中的具体布局是本例的推演。[R07][r07]

### 9.3 演唱会售票：体验吸引与明确决策共同组成流程

**假设情境：** 用户先了解演出并产生兴趣，再确认时间、场地、票档或座位，最后完成购买。

设计需要区分浏览与购票阶段。舞台素材、艺术家形象和主题图形可以构成强烈表现，具体色彩和节奏应来自真实内容与品牌。票档、场次、当前选择和费用等信息，则要支持清楚判断。

**可形成的决定：** 展示页围绕演出内容组织氛围；购票区域保留品牌，同时突出决策对象和反馈；页面切换时保留用户已经选择的场次与条件。

**交给 frontend-craft 的工作：** 协调主视觉与操作区域的对比和连接，安排必要的动效或媒体控制，并在真实场次名称、票档数量和状态下复核。

**验证问题：** 页面是否让人感受到这场演出的特征？用户是否能迅速知道自己选择了什么、下一步做什么？

**参考方法：** Carbon 根据操作与探索调整表达的思路，可用于理解不同阶段的需求；本例不声称任何特定票务网站采用了这套方案。[R05][r05]

### 9.4 AI 资料工作台：由核心工作决定功能的呈现方式

**假设情境：** 用户阅读材料时提问、核对引用并保存结论，希望下次继续当前工作。

如果只按功能列表设计，可能产生文档、对话、模型、设置等并列模块。产品理解需要进一步判断：用户的主要工作围绕资料、项目还是单次会话；引用与原文怎样对应；结果需要怎样保留。

**可形成的决定：** 将阅读、提问和引用关系组织在连续工作过程中；模型与连接设置放在合适的上下文中；保留当前资料位置与会话关系。具体结构根据项目事实选择，并非所有 AI 产品都必须使用三栏布局。

**交给 frontend-craft 的工作：** 用真实中文长文、引用和会话内容安排空间，区分主要工作区与辅助工具，控制重复帮助文字，保留必要的状态与反馈。

**验证问题：** 用户能否从问题返回对应材料并继续阅读？界面是否通过结构表达关系，而无需常驻的大段说明？长内容下是否仍然舒适？

这个例子最能说明本轮的目的：产品理解提供了“什么值得持续展示”的依据，视觉能力再把这些内容组织成好的界面。

## 10. frontend-craft 的最小改造

### 10.1 先检查现有内容，再决定是否需要添加

frontend-craft 已经进行过多轮优化。实施时应寻找已有任务理解、范围控制、视觉方向和复核指令，优先在原处合并，避免新增一套重复工作流。

| 可能涉及的位置 | 本轮要补足的行为 | 修改边界 |
| --- | --- | --- |
| `SKILL.md` 的入口或工作流 | 识别平台级任务；读取项目设计依据；在依据足够时直接推进 | 增加简短衔接，不复制产品设计方法全文 |
| `references/visual-style.md` 或对应章节 | 把当前任务、主体、真实素材和状态语义用于方向判断 | 保留既有配色、字体与细节知识；已有内容足够时不重复添加 |
| `references/review.md` 或对应章节 | 检查真实内容、关键状态和跨页面关系下的效果 | 不以“已经遵守规则”代替实际观看和操作 |
| `references/exemplars.md` 或对应章节 | 解释案例怎样从任务与内容走到视觉选择 | 少量完整推理即可，不扩成行业模板库 |

这些是待核对的仓库内相对位置，并不声明本地目录一定与表格完全相同。

### 10.2 可提炼的入口指令

以下文本表达目标行为，由执行 Agent 按现有语气整合：

> 开始前读取当前任务相关的产品或设计依据。对于从零建设整个平台、跨页面重设计或核心流程调整，先使用可用的 product-design 工作流明确核心任务、页面关系、展示重点和变化范围，再进行界面设计。已有依据足够时直接继续；局部或仅样式任务保持原范围。把真实内容与主要状态用于设计和复核，实施中出现实质冲突时更新对应依据。

### 10.3 可提炼的视觉衔接指令

> 根据用户当前要看、理解、判断或完成的事情确定视觉重点。结合实际素材、品牌与状态含义选择构图、密度、配色和表现力度。相同产品中的不同页面或区域可以有不同节奏，同时保持必要的一致性。设计理由保留在开发材料中，界面只呈现用户需要的内容。

这些指令不能替代原有审美判断和细节能力。不要以新增了 product-design 为由删去 frontend-craft 对页面目的和内容关系的理解。

### 10.4 必须保留的已确认方向

- 对冗余解释文案的克制，同时保留必要标签、条件、错误和操作后果。
- 对不同题材和视觉表达的开放，允许品牌、氛围、材质与丰富色彩。
- 对用户认可的品牌和设计决定的尊重。
- 对颜色关系、前景背景配对、字体与细节一致性的判断。
- 根据任务范围选择工作量，避免默认生成大量 Demo 或评测矩阵。

## 11. 新 Skill 的建议组织方式

### 11.1 名称与描述

建议名称为 `product-design`。名称主要承担发现与触发，具体中文定位可写为“产品体验设计”。如果仓库已有等价能力，应评估合并而非重建。

描述应明确能力及触发情境。可参考：

> 为网站、软件和平台的新建、整体重设计及跨页面体验调整建立产品与设计依据：理解用户任务、核心内容、对象和流程，确定页面职责、展示重点与整体表现方向，并衔接界面实现和验证。适用于平台级设计或影响核心流程的改造；局部样式、明确组件调整和纯业务逻辑任务按现有工作流处理。

这段文本是语义草案。前置信息格式、版本字段和描述长度按 SkillMarket 当前规范调整。

### 11.2 建议文件分工

| 文件 | 建议职责 |
| --- | --- |
| `product-design/SKILL.md` | 任务范围、最短完整工作流、产品理解到展示重点的连接、与 frontend-craft 的衔接、反馈原则 |
| `product-design/references/product-context.md` | 证据读取、重要未知、项目上下文的内容与维护、最小交接 |
| `product-design/references/new-and-redesign.md` | 新建、存量重设计及继续建设的不同判断 |
| `product-design/references/examples.md` | 少量有来源的成熟案例，以及明确标为推演的应用示例 |

这是可压缩的初版结构，不是要求必须凑满的文件列表。内容较少时合并；主文件应能独立说明关键行为，并明确什么时候读哪个参考。

初版通常无需增加脚本、模板生成器、项目扫描器或强制目录结构。只有发现明确、重复且值得自动化的工作，再增加工具。frontend-craft 的配色与细节知识继续保留在原处，不在新 Skill 复制第二套。

### 11.3 运行内容与维护材料分开

运行内容保留可执行判断、必要示例和少量关键来源。本文的完整论证、来源比较、实施取舍和验证记录放在仓库约定的维护位置。

主文件不应要求每次都阅读完整方法论、所有参考或全部案例。维护材料也不应通过多层引用重新变成隐性的必读输入。

## 12. 实施顺序与验证方式

### 12.1 先核对本地，再编写最小可用版本

1. 读取仓库规则与最新本地内容，确认已有能力和改动边界。
2. 提炼本轮的核心行为，先形成新 Skill 的主工作流与必要参考。
3. 修改 frontend-craft 的对应入口和复核位置，合并重复指令。
4. 依据仓库现行规则更新发现入口、索引或版本信息。
5. 检查指令和引用是否可执行，完成有针对性的试用并记录结论。

先把一个合理版本做成可使用的 Skill，再通过真实任务调整。不要先制作完整产品方法论库，再等待未来使用证明价值。

### 12.2 文本与结构检查

优先复用现有检查能力，确认名称、元信息、路径、引用与仓库规范一致。重点排查：触发是否重叠、是否会循环交接、缺少配套 Skill 时是否无故中断，以及局部修改是否被扩大成平台重设计。

检查本轮新增指令是否会诱发以下行为：编造用户画像；把所有功能都做成菜单；把品牌保留等同于冻结全部旧样式；默认问一长串问题；强制生成多个风格方案；把分析结果变成页面常驻说明。

### 12.3 小范围检验行为，避免重复建设评测工程

若本地已有适合的真实任务和材料，直接复用。若暂时没有，可用少量文本任务检查边界：一项新建任务、一项存量重设计任务，以及一项应保持局部范围的样式任务。无需为这几个检查额外开发页面或通用测试框架。

使用独立 Agent 做文本检查时，明确限定只输出需要的信息、拟采取的步骤或关键设计判断，不写页面或项目文件。给它 Skill 与原始任务材料，不提供预期设计答案或本轮的诊断结论。检查它选择的行动和产出，避免把复述指导文件当作能力验证。

文本任务只能说明指令和分流是否合理，不能证明视觉质量提高。

### 12.4 用真实项目检验整体收益

当用户指定了可使用且已授权的产品工作区时，选择一条有代表性的真实核心流程：记录原状与具体不满，形成关键设计决定，使用 frontend-craft 实现，再查看结果。

真实内容、主要任务和合理的查看条件应保持可比较。重设计允许修改结构和内容组织；比较时需要说明哪些变化发生了，不把同时改变的多项因素包装成某一条规则的因果证明。

分别检查：

| 检查维度 | 需要的证据 |
| --- | --- |
| 产品理解 | 主要设计决定对应用户意图、内容或已知约束，并实际改变了页面 |
| 任务与流程 | 能沿着核心路径完成目标，跨页信息与状态关系成立 |
| 视觉质量 | 真实内容下的实际画面，及针对重点、关系、表现力和细节的具体判断 |
| 实现质量 | 涉及的交互和状态能够运行；相关工程检查通过 |

当前任务仅授权制作 Skill 时，先完成 SkillMarket 内的工作；不要把验证要求扩展成擅自改造另一平台。真实产品材料暂缺时，明确记录“真实产品效果待验证”，无需制造理想化 Demo 来填补证据。

### 12.5 根据失败位置迭代

如果产品理解与流程改善而画面仍普通，应继续检查视觉方向、素材与实现；如果分析更完整却没有影响界面，应改善从分析到决定的转化；如果局部任务变慢或频繁提问，应收紧触发和信息收集范围。

每轮只修正有证据的缺口。已有规则足够时不增加相似表述，单次用户偏好也不应直接升级为通用禁令。

## 13. 完成标准与常见误解

### 13.1 本轮制作完成的标准

新 Skill 可以被发现并执行，能够区分新建、重设计与局部任务；能形成影响内容、流程与视觉的具体决定；上下文能够被 frontend-craft 使用；两个 Skill 的知识没有大面积重复；相关引用和仓库结构检查通过。

交付应说明修改了什么、为什么这样划分、做了哪些实际验证，以及哪些效果尚无证据。Skill 文件完成与真实平台效果提升是不同层面的完成状态，应分别报告。

### 13.2 最容易出现的误解

| 误解 | 应保持的判断 |
| --- | --- |
| 新 Skill 就是先写一份更长的 PRD | 产出要能影响页面、内容和视觉决定，并进入实现 |
| 理解用户就是增加大量问题 | 先使用材料，只补会改变方案的重要未知 |
| 功能服务用户，所以装饰都应删除 | 品牌、情绪、欣赏与探索也可以是用户价值 |
| 每个行业应该固定一种风格 | 结合当前任务、真实内容、品牌和使用阶段选择 |
| 全站统一就是所有页面相同布局 | 统一共同语义与视觉关系，保留职责需要的差异 |
| 重设计必须推翻旧页面或旧品牌 | 根据问题与用户要求决定保留和改变的内容 |
| 新 Skill 接管产品，旧 Skill 只管 CSS | frontend-craft 继续承担页面级设计判断 |
| 流程越完整、候选越多越可靠 | 工作量由实际未知和变化范围决定 |
| 规则通过即可证明页面更美 | 需要真实画面和实际使用的证据 |

## 14. 给执行 Agent 的任务摘要

请在 SkillMarket 当前本地工作区中，先阅读仓库规则及 frontend-craft 的最新实现，再按本文新增轻量的 product-design，并对 frontend-craft 做必要的衔接修改。重点是把产品价值、用户当前任务、真实内容和核心流程转成可执行的内容、布局与视觉决定。为从零搭建和已有平台重设计保留不同分支，复用已经确认的项目上下文；让 frontend-craft 继续完成页面设计与实际效果打磨。借鉴本文列出的真实 Skill 与设计系统方法，同时保留来源事实与本项目推演的区别。将详细论证留在维护材料中，运行文件保持简明。按当前仓库约定完成检查和交付，报告实际验证范围；避免额外扩建 Demo、评测基础设施或修改未纳入任务的产品项目。
