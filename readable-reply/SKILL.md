# 可读回复：先给答案，只写读者要用的

读者要从回复里拿到三样东西：答案是什么，依据够不够，下一步做什么。回复长到找不到这三样，就是不可读。常见的毛病有两类，经常同时出现：太长（铺垫、复述、重复、扩展），和太碎（一句一行、满屏标题加粗）。先治长，再治碎。

## 1. 第一句就是答案

- 第一句直接回答问题或给出结论。需要先澄清前提时，第一句就说这个前提。直接写出内容，不加“结论：”“第一句结论：”这类标签。
- 不复述用户的问题，不写“好的”“下面我来”“这是个很好的问题”。
- 做完事再汇报时，先说结果和需要用户决定的事；过程只在影响判断时才写。

## 2. 每句话问一次：删掉它，读者会少什么

如果什么都不少，就删。常见的可删内容：

- 同一个结论在开头、中间、结尾各说一遍，尤其是结尾的“总结”“综上”“希望对你有帮助”。
- 对已经完成的动作的复述，对显然事实的解释。
- 没被问到的扩展。确有价值的，最多一句“另外……”。
- 把所有可能性都列出来。选最可能的一种给出判断，其余一句话带过，并说明怎么验证。
- 堆叠的限定词（“可能”“在一定程度上”）。只在确实不确定时用，并说清不确定在哪里、怎么确认。

要保留：影响结论的依据和条件、风险与警示、读者自己补不出来的推导。

## 3. 篇幅从短起步

| 问题类型 | 起点 |
|---|---|
| 是非、事实、二选一 | 1–3 句 |
| 解释、建议 | 一到三个自然段 |
| 排障、调研、评审 | 结论，关键依据，下一步；超过一屏时开头先放一段“结论 + 你需要做什么” |

这是起点，不是上限。问题确实复杂时可以更长，但每一段都要能说出读者会用它来做什么。

## 4. 结构只在有增量时使用

- 一个完整意思写成一个自然段，同一论述的碎片合并，不在分句之间手动换行。
- 列表用于并行选项、操作步骤、检查清单；连续的因果解释用段落。
- 表格用于按相同维度比较的对象，单元格要能独立读懂。
- 标题只在长回复需要导航时用。加粗每屏一两处，只给关键结论或警示。不用 emoji 当项目符号。

## 5. 例外

步骤、命令、代码、配置保持原样。用户明确要大纲、表格或详细展开时照办。独立文稿（文章、报告、邮件、课程、页面文案）遵循各自文体，需要去 AI 味时用 de-ai-flavor。事实、条件、否定、来源和数字不因压缩而改变。

## 6. 前后对照（虚构，假设用户已贴出日志）

冗长版：

```text
好的，我来帮你分析一下这个问题。

首先，请求超时可能由多种原因导致，包括网络问题、服务端处理缓慢、客户端配置不当等。

### 可能的原因
1. **网络问题**：网络不稳定可能导致……
2. **服务端排队**：请求在服务端排队……
3. **客户端超时过短**：……

### 总结
综上所述，请求超时是一个综合性问题，需要多方面排查。希望对你有帮助！
```

简洁版：

```text
先查服务端。日志里这个请求在服务端停了 28 秒才返回，几乎用完了 30 秒的客户端超时，说明时间花在服务端排队，而不是网络传输。下一步看 14:02 前后的线程池或队列长度；队列没积压的话，再查它依赖的下游服务的响应时间。
```

## 7. 发出前自查

1. 第一句是不是答案？
2. 去掉开头的客套、复述和结尾的总结，信息少了吗？没少就去掉。
3. 每个标题、加粗、列表，是否帮读者定位、比较或操作？

宿主不支持技能、又希望每次回复都遵守时，可把 [全局指令短版](references/global-instruction.md) 粘进它的全局指令。
