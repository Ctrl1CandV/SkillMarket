# 收尾：回到开工时定的，逐条验

收尾要回到开工确认单。开头定下的需求、倾向和验收条目，每一条都要有结论和证据。

**先认清自己的角色。**

- 这次的代码是你写的，你就是**开发者**，按下面第 1 到第 5 步做。
- 你是被派来的，或者在新会话里收到了审查请求，你就是**审查者**。读 [references/reviewer.md](references/reviewer.md)，照那里做。

## 1. 找到依据和范围

读 `docs/briefs/` 里这次的确认单。

没有确认单时，从用户最初的请求和对话里整理出验收条目，标明“收尾时补写”，请用户确认后再继续。

再确定改动范围：从开工时的那次提交到现在的提交（用 `git log`、`git diff <起点>` 查），加上还没提交的改动。

完成标准：手上有确认单（或用户确认过的补写条目），改动范围也明确了。

## 2. 开发者自测

确认单里标给开发者的条目由你来测，测那些要了解实现才测得准的地方，比如边界输入、你知道的风险点、核心算法的已知答案。按确认单定的验证档位来做：

- 要测试的：跑测试，贴出命令和结果。
- 要运行的：实际运行主要用法。
- 有页面或图像的：实际打开并截图。装了 `frontend-craft` 就用它的检查脚本。

没通过的，先修好再往下走。

完成标准：每个开发者条目都有证据（命令和输出，或截图路径），或者标明“不通过”并写出原因。

## 3. 交给独立审查者

这一步不能省。审查要交给没参与开发、带着新上下文的审查者，可以是同一个模型。

1. **宿主能开子代理**（Claude Code 的 Agent、Codex 的 spawn_agent、pi 的 subagent 扩展）：开一个新的子代理，把 reviewer.md 末尾的“派审查者时的说明”填好交给它。
2. **宿主不能开子代理**：把同样的说明写进 `docs/briefs/<确认单同名>.review-request.md`，请用户在项目目录里开一个新会话，告诉它“用 dev-acceptance 审查这份请求”。用户同意的话，也可以用宿主命令行的非交互模式，以子进程运行这份请求，比如 `claude -p`、`codex exec`、`pi -p`。

交给审查者的只有四样：确认单、改动范围、运行方法、你的自测结果。自测结果只作为待核对的说法。实现过程中的讨论和你的判断都不交给它。

完成标准：拿到审查者对每个条目的结论。

## 4. 修复与复核

按审查结论修改。修过的条目重新自测，再请审查者复核这些条目：可以让同一个子代理接着看，也可以再开一个新的。

缺设备、缺数据、需要用户本人操作等确实验证不了的条目，保留“没验证”和原因，不算通过。

完成标准：每个条目都已有结论：
- “通过”；
- 写明原因的“没验证”；
- 用户同意保留的“不通过”。
其余“不通过”的都已修完并复核。

## 5. 记录、提交、汇报

- 把每条的结论和证据位置填进确认单的“验收结果”，写明审查方式：子代理、新会话、子进程，或者为什么只能自审。
- 长期项目：更新已有的管理文档，比如 STATUS、CHANGELOG、README。
- 提交：把这次的功能或重做作为一个完整单元提交一次，代码、测试、确认单和文档放在一起。提交写法按项目约定，装了 `git-governance` 就用它。推送、开 PR、合并，等用户开口。
- 向用户汇报：每条的结论、没验证的条目和原因、审查方式。
