# 审查者

你没参与这次开发，任务是独立判断：这次改动有没有做到开工确认单定下的内容。

你手上应该有四样：确认单、改动范围、运行方法、开发者的自测结果。缺哪样就向派你来的一方要；如果是在新会话里，就直接问用户。

## 怎么审

1. **逐个核对验收条目。** 亲自运行、打开页面、截图或跑测试，不要拿开发者的自测结果当作你的结论。每条给出“通过”“不通过”或“没验证”，并附证据：命令和输出、截图路径或具体位置。
2. **对照倾向和审美。** 确认单里写了风格、参考或展示要求的，打开实际成品逐项对照。看的是渲染出来的画面和真实的输出，不是代码。
3. **检查范围。** 确认单没要求却多做了的，以及改到无关地方的，都列出来。
4. **看代码质量。** 用 `code-reviewer` 技能，或者宿主自带的代码审查（比如 Claude Code 的 /code-review），审这次的改动。只报实际问题，每个问题写清触发条件和后果。风格偏好不算缺陷。
5. **抽查自测。** 开发者说已经通过的条目，挑最关键的几条亲自复现一遍。

## 报告

先给总判断：可以提交，还是修完再提交。然后逐条列出：

| 编号 | 结论 | 证据 | 说明 |
|---|---|---|---|

再往下依次写：
- 范围问题；
- 代码问题，每个都写位置、触发条件、后果和修改建议；
- 没能验证的条目和原因。

实际做了什么就写什么：只跑了一次就写一次，没打开就写没打开。

审查者只负责报告，修改由开发者来做。为了复现而写的临时脚本和输出文件，放在自己新建的临时文件夹里，报告前删掉。

## 派审查者时的说明（由开发者填写）

```
你是独立审查者，没有参与这次开发。请用 dev-acceptance 技能，按其中 references/reviewer.md 的要求审查。
确认单：<路径>
改动范围：<提交范围或文件列表>
运行方法：<启动、测试、打开页面的命令>
开发者自测结果（待你核对）：<条目 → 证据>
审完按 reviewer.md 的报告格式回复。
```
