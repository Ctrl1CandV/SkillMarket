# 排错：先有会变红的命令，再找原因

**先看问题大小。** 报错信息已经直接指出原因的，比如拼写、路径、配置不一致、缺依赖，直接修，修完重跑原来的操作确认，就算结束。其余问题按下面五步走。

**先遮掉凭据。** 要展示的命令、输出和日志里，凡是出现密钥、令牌、Cookie，一律写成 `<REDACTED>`。复现命令从环境变量读取凭据。

## 1. 做一条会变红的复现命令

这是排错的核心。找到一条命令，一跑就能看到用户说的那个症状（变红），修好之后它会变绿。按这个顺序考虑：

1. 一个失败的测试，放在能触到这个 bug 的那一层。
2. 对运行中服务的 curl 或 HTTP 脚本。
3. 带固定输入的命令行调用，与已知正确的输出对比。
4. 无头浏览器脚本（如 Playwright），断言页面、控制台或网络请求。
5. 回放抓下来的真实请求或数据。
6. 只启动系统一小部分的临时脚本。
7. 结果“有时不对”时，用随机输入跑很多次。
8. 在已知正常和已知出错的两个版本之间二分，用 `git bisect run`。
9. 同一份输入分别跑新旧两版或两套配置，比较输出。

必须由人来操作的，写出逐步指令，收集他的输出。

命令要**紧**：几秒内出结果，每次跑的结论一样，断言的是用户说的那个症状，而不只是“没崩溃”。

- **时好时坏的 bug**：目标是把复现率提到能调试的程度，办法有循环、并发、加压、缩小时间窗口等，并报告实测的复现率。
- **性能问题**：先测出一个可以比较的基线，分清冷启动、缓存和实际处理各占多少。

做不出复现命令时，停下来，说清楚试过什么、还缺什么证据。向用户要以下三样之一：能复现问题的环境；遮过凭据的日志或录屏；允许加临时诊断代码。这时得出的结论都标为“推测”。

完成标准：写出这条命令，已经至少跑过一次并贴出输出，而且它确实在这个 bug 上变红。

## 2. 确认，再缩小

先确认红的是用户说的那个症状，而不是旁边另一个错误。

然后一次删掉一样东西，可以是输入、调用方、配置、数据或某个步骤，每删一次重跑一次。最后剩下的每一样都缺一不可。

完成标准：再删任何一样，命令就会变绿。

## 3. 提出可证伪的猜想

动手验证之前，先列出两到五个猜想，并排好顺序，免得锁死在第一个念头上。

每个猜想都写成这种形式：“如果原因是 X，那么改 Y 会让 bug 消失，改 Z 会让它更严重。”写不出预测的猜想，要么删掉，要么改清楚。

把排好的清单给用户看一眼。他常常知道最近改过什么，或者已经排除过哪些可能。用户不在，就按自己的排序往下走。

## 4. 一次只改一个变量

每次探查都对应某个猜想的预测。

- 优先用调试器或 REPL 查看状态。
- 要打日志，只打在能区分不同猜想的边界上，每条加一个唯一前缀，如 `[DEBUG-a4f2]`，收尾时搜一次就能删干净。
- 性能问题少用日志，主要靠测量和二分。

猜想被否定也是证据。这时回到第 3 步重新排序，不要在错误的原因上继续打补丁。

## 5. 修复、锁住、清理

- **锁住**：如果有一个测试位置能体现 bug 的真实形态，先把缩小后的复现写成失败的测试，看它变红；修复后看它变绿；最后再跑一遍第 1 步的原始命令。如果没有合适的位置，这本身就是一个发现，写进汇报：现在的代码结构锁不住这个 bug。要改接口，可以用 `codebase-design`。
- **修复范围**：只改到原因为止。
- **检查**：跑项目里相关的测试、类型检查或构建，区分原本就失败的和这次弄坏的。只跑了局部，就说只跑了局部。
- **清理**：搜出 `[DEBUG-` 前缀的日志并删掉；临时脚本删掉，或者移到标明用途的调试目录。
- **汇报**：写明原因（被证实的那个猜想）、改了什么、跑过哪些检查、还剩什么限制。提交说明里也写上原因，方便下一个排错的人。
