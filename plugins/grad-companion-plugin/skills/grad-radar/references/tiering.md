# 分级规则（每日发现：筛选）

> **本文件是启发式，不是权威。** 排序结果是「启发式排序，不是质量判断」——它只反映与当前学习目标的关系，不评价论文好坏。每次输出必须带上这句话。

## 两个概念必须分开（旧版把它们混在一起）

- **推荐级别（tier）**：`must_read` / `skim` / `archive`——**当次简报里的呈现档位**，数量由 `.grad/config.json` 的 `daily_caps` 决定（新起点 must_read 1 / skim 2；自定义值照用；0 表示该类不安排）。用户侧文案呈现为「优先关注 / 可以速览 / 其他候选」，避免强制任务感。
- **重要性（importance）**：core / relevant / peripheral——论文与学习目标的**关系属性**，记在单篇主记录的 classification 里。

tier ≠ importance：must_read 不自动等于 importance=core（今天可能只是 deadline 临近）；core 论文也不必出现在今天简报里（在读的可能早已登记）。反过来，归档一篇也不意味着它不重要——只意味着本次不投入。

## 三级定义

| 级别 | 上限 | 含义 | 产出 |
|---|---|---|---|
| **must_read** 优先关注 | `daily_caps.must_read` | 与当前目标直接相关、值得今天或近几天投入 | 用户选中后进单篇阅读协议（quick/standard/deep） |
| **skim** 可以速览 | `daily_caps.skim` | 相关但非核心：相邻方法、下游应用、值得知道的动态 | quick 卡片或一句话；选中才升档 |
| **archive** 其他候选 | 不限 | 其余 | **简短索引：id + 标题 + 一句可回查的理由**；不为其生成摘要长文 |

正文不超配置数量；不足不凑数，可以把建议花在「继续已有阅读」上。超上限时按信号强度截断，被截掉的降一级，不丢弃。

## 优先关注信号（满足越多越强）

1. 摘要同时命中课题核心词两组以上（如 agent + LLM + planning/tool-use/memory 中的两个）
2. 提出或实质性改进一个方法（不是只做应用/套壳）
3. 直接的竞品工作：与正在做的 idea 解决同一问题
4. 新 benchmark / 评测协议 / 已有 benchmark 的缺陷分析
5. 复现失败报告（negative findings）——信息量高
6. **基础性/经典工作**：虽旧但支撑当前学习路线（新论文引用密集出现、用户正读的书/论文的前置）——旧不是降级理由

## 速览信号

- 只命中一组核心词，或只与课题外围相关（agent 的某个下游应用域）
- survey / 综述（**除非正好覆盖课题方向**——基础综述可能是 core，重点给知识分类与入门顺序，不套「实验提升多少」模板）
- 方法相关但场景差异大（纯机器人、纯游戏）

## 归档信号

- 仅分类沾边但关键词不命中；明显属于其他子方向（纯 CV、纯理论、纯硬件）
- 重复投稿/旧文新发（标题与已见条目高度相似）——仍要保留索引，不猜身份合并

## 理由的写法（硬要求）

每一篇、每一级都要写理由，格式：**理由 = 命中的具体信号 + 引用的原文片段**。理由必须可反驳——用户说「这篇应该优先」时，判断依据暴露出来，才知道该改关键词组还是改规则。

- ✅ 「优先关注：命中 agent+LLM+benchmark 三信号，摘要称提出新的 multi-agent 评测协议」
- ❌ 「必读：感觉相关」「顶会论文，建议精读」（会议名不是信号）

## 用户反馈回路

用户对分级提出异议时：

1. 异议合理 → 修正 `config.json` 关键词组（`radar_config.py` 改后 validate），下次生效
2. 规则本身盲区（如「benchmark 论文一律优先」没写进规则）→ 修改本文件对应小节
3. 本次异议追加到当日简报末尾「分级调整记录」，修正过程可追溯
4. 涉及**论文本身**的重要性/难度（不只是今天排哪）→ 走单篇流程的 `update-context`（记入主记录，附理由），不改本文件
