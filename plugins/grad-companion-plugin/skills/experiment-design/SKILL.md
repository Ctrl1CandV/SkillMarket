# experiment-design：从研究问题到最小判别实验

目标是让一次有限投入能改变研究判断：做什么比较、排除哪种解释、结果不同分别怎么办。优先服务学生的计算研究项目；按实际问题选设计，不把每次讨论扩成完整论文实验套装。

## 先找到本次要作的判断

复用用户已给出的研究问题、论文、代码、数据和资源约束；有本地材料先读相关入口。已有方案则先找影响结论的缺口，保留合理部分。区分用户事实、已核实的外部证据、设计建议和待确认条件。

用一句话说明“在什么条件下，改变什么，预期影响哪个可观察结果”，再指出当前最需要排除的替代解释。例如分数提高可能来自新增模块，也可能只来自更多调用或调参。不要把希望得到的结论写成事实，也不预先承诺创新性。

缺资料时先给能确定的方案。只追问会改变第一轮设计的关键项，如数据能否访问、现有基线、预算上限；未知费用和方差明确标注，给计算方式或先导测量。不编造用户的模型、设备、论文结果、命令或文件路径。

## 形成最小的有效比较

每个实验条件都应回答一个问题；删去不会改变当前决策的组合，留下必要对照。

- **主比较**：选择最接近研究问题的可用方法与合理简单基线，说明选择原因。论文分数只有在数据划分、指标和预算等设置可比时才能直接对照；未核实的方法标成候选，不写成“最强基线”。需要补查时读论文或作者代码的一手材料。引用论文结果前，先在自己的数据与管线上复现主基线，接近报告值再比较新方法；差距明显时先查实现、数据版本与设置，不拿偏弱的基线衬托改进。
- **余量与健全性**：投入完整比较前先看值不值得做。用上限条件（如给出正确检索结果、真实标签或理想的中间输出）估计可提升空间，用随机、多数类、照抄输入等平凡基线确认任务和指标能区分好坏。余量很小，或平凡基线已接近主方法时，先调整问题或评测，不急于扩大实验。
- **公平条件**：固定不属于研究问题的差异，包括数据与划分、模型版本、输入信息、训练/推理预算、调参机会、评测器。若成本本身是贡献，就比较同质量下的成本或同预算下的质量，保留原方法的正常运行点；不能把方法的关键能力强行裁掉，再声称比较公平。
- **机制对照**：消融用来区分具体解释。关模块若同时减少调用或参数量，必要时加等预算或替代模块对照。怀疑模块交互时再做相应组合；不默认穷举全部子集。
- **实验单位**：说明结果面向哪些任务/数据集/对象，哪一级是独立样本，哪些是同一对象的重复测量。按真实对象、时间或来源划分数据，防止训练、调参与最终评测之间泄漏。
- **运行安排**：同一任务或划分能配对比较时保留配对；机器、批次或时段可能影响测量时，交错运行或分块控制。重复 seed 与新增独立任务回答不同问题，不互相顶替。

## 让结果可以解释

先定主要结果及方向，再选必要的诊断指标、失败类型和切片。写清单位、聚合方式、超时/失败是否进入分母、关键成本或质量约束，避免只保留成功样本。

正式比较前确定最小有意义改善或可接受退化；依据来自实际用途、既有证据或明确的暂定假设。不要把模型随手给出的百分比包装成领域标准。重复次数由差异尺度、已有波动、独立单位数量与预算决定；没有依据时安排小规模先导，目标是查通路、估成本和波动，不能把它当最终效果证明。

涉及 seed、置信区间、LLM 评审、多个切片或顺序追加样本时，按需读 [references/measurement.md](references/measurement.md)。分析方法必须匹配配对、分组和重复结构；说明不确定性来自什么。预算不足以支持预期精度时，缩小结论范围或延后主张，不用统一“3 个 seed”或一个 p 值代替论证。

把可能结果与行动提前对应：

- 差异达到有意义范围、关键约束满足 → 扩展到新的任务/条件，检验外推；
- 差异小且不确定性大 → 依据预定预算判断是否补充独立信息；当前结论可以是证据不足；
- 消融/等预算对照削弱原解释 → 修正机制主张，保留实际有用的工程收益；
- 实现错误、数据异常、OOM 或配置不通 → 先排障，不能据此否定研究假设。

以上是可调整的判断框架，不是自动宣判。看过结果后改变指标、阈值、样本选择或分析方式，要记录理由，并把新增分析标成探索；不追逐显著性反复追加直到“成功”。

## 排预算和执行顺序

把计划分成可立即开展的最小判别轮与有条件追加的实验。先导只在实现、成本或方差未知时需要；已有可靠测量不必重来。

预算按实际矩阵核算：各条件的任务数 × 每任务重复 × 单次费用/耗时，再加训练、调参、评审、失败重试及准备成本。共享训练与按任务推理分开计，墙钟时间与 GPU 小时分开写。未知量给范围或公式，并标依据；资源上限优先约束方案规模。

写清达到什么条件才进入下一轮，以及预算、失败率或证据不足时在哪停。使用已有真实命令/配置时给可追溯入口；没有入口就给需要实现的操作及验收条件，不生成看似可运行的虚构命令。设计请求本身不启动训练、付费调用或申请资源；已有明确执行授权时可交给执行流程，不重复索要许可。

## 交付与衔接

简短讨论直接给一份紧凑方案；需要持久化、执行交接或多轮设计时，可裁剪 [assets/experiment-plan.md](assets/experiment-plan.md)，省略无关栏目。遵循项目现有路径；没有约定时可用 `.grad/plans/<有意义的短名>.md`。用户只讨论时不默认写盘。修订保留版本与变更理由，特别是哪些决定发生在看结果之后。

交付至少能让执行者知道：**要区分什么解释、比较哪些条件、测什么、要花多少、结果如何影响下一步**。区分“可开展最小轮次”“待补条件的草案”和“只能做探索”，把真正阻塞项放在对应步骤。

- 已有 `idea-ledger` 时引用真实 `idea_id` 和方向记录；没有时直接写研究问题。设计方案不自动登记候选或更改方向状态。
- 已有 `run-provenance` 时，计划保留未来需要记录的配置、版本、指标口径与分组依据，实际运行后再由它登记 run 和 claim。不得把计划或作者结果登记为本人 run，不预填 `support`，不替用户确认 `experiment_group`。
- 两者都不可用也能完成设计：在普通 Markdown 中保留问题、方案、来源与待执行记录要求，不创建替代台账系统。

最后检查：若各候选解释都会产生同样结果，这个实验还没有判别力；若结论需要的条件没有测到，缩小主张；若执行者还得自行猜关键条件，把方案标为草案并指出缺口。
