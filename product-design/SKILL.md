# Product design

让产品理解进入画面：用户为什么来，决定什么值得展示；内容与任务的关系，决定怎样组织；当前需要关注什么，影响尺度、对比、颜色与空间。分析应落到具体设计决定，不能止于用户画像、功能清单或一份更长的 PRD。

用户价值也包括欣赏、期待、探索、信任与记忆。表达可以鲜明、丰富、安静或紧凑，依据来自当前任务、真实内容与品牌。行业名称不能直接决定整站色板、密度或布局。

## 先判断本次变化

读用户要求、项目约定和已有产品或设计依据，明确本次处理的产品或子系统、主要任务、可改范围，以及交付是评审、方案还是实现。用户当前要求优先于已有依据，项目已确认的决定优先于本技能的默认方法。

| 情况 | 从哪里开始 |
| --- | --- |
| 从零建设产品 | 建立核心对象与第一条完整任务流程，让品牌、素材和体验方向一起进入设计 |
| 重设计或新增能力影响核心流程、角色、导航或页面关系 | 查看现状与问题，确定保留和可变范围，只重审受影响的决定 |
| 已有充分依据，继续建设页面 | 直接读取并落实；只补本次新增的内容和约束 |
| 不涉及核心流程或页面关系变化的单页、组件、局部修复或样式调整 | 在当前范围内完成，使用可用的 frontend-craft，不补做全平台分析 |

按变化的实质分流：一页也可能重构核心流程，几十页换主题也可能只涉及样式。纯业务逻辑任务按工程流程处理。仅请求评审或方案时交付相应内容，不扩大为实现。

## 从理解到实现

### 1. 找到足以开始的依据

先读产品说明、用户原话和已确认决定，再粗看相关页面、路由、对象、角色与素材；有运行条件时走查本次涉及的流程。区分建设者偏好、最终使用者的任务、代码及运行事实，以及计划中的能力。已有功能不自动拥有最高优先级，当前 CSS 也不自动成为品牌规范。

只有材料无法回答、且会改变主要任务或已有承诺的未知才需要询问。可逆细节自行判断；假设写清依据和影响，不能编造访谈、画像或行为数据。先解决影响设计的重要未知，在内容与实现中继续校正，不等待完整调研才开始。

### 2. 确定对象、流程与页面职责

找出用户围绕什么对象工作、对象怎样关联，以及从进入、判断、行动到取得和继续使用结果的过程。对相关页面说明用户在这里要看见什么、判断什么、做什么，操作后到哪里；同时考虑关键状态和上下文怎样延续。

以任务组织导航与入口，不把接口、数据表或功能目录逐项变成菜单。能力是否保留、入口在哪里、何时突出展示分别判断；不同职责可以在一页共存，不必为每项能力新增页面。

### 3. 把依据转成可执行的表现方向

重要决定应串起 **依据 → 设计决定 → 界面影响 → 检查方式**。用简短文字或表格即可，不能只写“现代、专业、简洁”。例如用户必须比较两个对象，就要安排共同可见的比较属性和稳定对齐，并用真实差异检查是否能完成判断。

- **分配视觉地位。** 区分主要对象、判断依据、当前动作与次要工具；明确哪些先看到、哪些同时比较、哪些在相关时出现。重点也可以是一组数据、一段正文或一件作品，不总是大标题或按钮。
- **让内容进入设计。** 尽早使用真实或脱敏材料；缺少数据时用符合实际长度、数量差异和状态的样本并标明。不要为整齐删必要字段、缩短所有标题或把复杂内容替换成等长卡片。关键素材不足时记录其影响。
- **把体验落实到视觉关系。** 结合使用节奏、品牌、素材和参考，说明主体、密度、图文关系与表现力度；区分品牌、状态、数据、内容素材和氛围的颜色作用。同一产品的浏览、阅读与确认区域可以有不同节奏，共同语义与视觉身份仍须连贯。
- **借鉴可解释的关系。** 指出参考中哪种内容关系或表达手法适合当前任务，改变了哪个决定；不复制行业模板。配色、字体、材质和页面构图的具体解法交给页面设计继续深化。

设计依据留在项目材料中，界面呈现使用者需要的内容。普通视觉细节由页面设计解决；新事实影响主要任务、跨页面关系或已确认约束时，才回到对应判断。

### 4. 保存依据，衔接具体设计

持续建设时，优先更新项目现有产品或设计文档；它们分工清楚时用短索引连接。没有合适位置才建立一份简短设计依据，例如项目约定目录下的 `design-context.md`，不强制路径或多文件体系。仅讨论或评审时可在交付中说明，不额外写项目文件。

让后续设计能直接获得：**当前任务与完成标准、真实内容与必要状态、对象及页面关系、保留与可变范围、视觉重点及依据、优先验证的结果**。已经存在的内容直接复用，不重新制作交接包。区分已确认要求、可定位的事实和设计提议；只维护会影响后续工作的决定。

Web 界面有 frontend-craft 可用时，按宿主机制读取其相关能力，继续完成页面级内容、构图、样式和交互。无需两个独立 Agent，也不依赖固定的兄弟目录。配套技能不可用时，依据项目规范继续设计与验证；不因缺少文件名停止或擅自安装。原生界面按相应媒介能力落地，不套用 Web 的实现验收。

### 5. 用代表性体验校正，再完成约定范围

交付包含实现时，先在已有工程中完成能体现核心价值和约束的一条流程，包含必要入口、内容、操作、结果及相关状态。方向明确时直接深化；只有实际分歧影响选择才做最小必要的比较。独立原型只用于隔离不确定问题或用户要求，不默认新增展示站与风格 Demo。

用真实内容查看画面并操作：主要任务能否完成，跨页对象、选择与状态是否连续，主体和表现力是否成立，工程实现是否可靠。目标理解有误就修正依据，结构有误就调整流程，画面普通就继续改进视觉关系，实现失真就修复实现。将成立的关系扩展到本次其余范围，不能以代表性流程通过代替全部交付。

交付说明重要决定及依据、实际改动与验证范围、尚未确定的内容。区分已实现、已静态检查、已看画面和已实际操作；没有查看或运行条件时说明具体缺口。文档齐全、遵守规则或构建通过都不能证明体验与视觉质量提升。
